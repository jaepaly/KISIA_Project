> **공동 소유: C 신정현 · D 박재현**
> 상태: **합의 대기** — C의 초안([howto/c-public-data.md §8](../roles/howto/c-public-data.md))에 D가 검토·보완한 판이다.
> 확정일: 2026-__-__ · `dict_version`: `geo-2026-__`

> 📌 **읽는 법.** §1~§5는 C의 초안을 그대로 유지했다. **D가 더하거나 바꾼 곳은 「D 검토」로 표시**했고, 초안의 미결 3건에는 D의 제안을 채워 넣었다. 신정현이 확인하고 이견만 코멘트하면 된다.

## 0. 왜 공동 소유인가

D의 가명화(`신갈동 → [경기 남부의 특정 동]`)와 C의 특정성 계산(`신갈동은 몇 명으로 좁히나`)은 같은 사전을 요구한다.

**가명화기 = 특정성 엔진의 역함수.** 사전이 어긋나면 복원이 깨진다.

## 1. 키

| 항목 | 확정 |
|---|---|
| 키 | **행정동 코드 10자리 문자열** (`"4146351000"`) |
| 왜 문자열인가 | 숫자로 파싱하면 앞자리 0이 소실된다 |
| 계층 | 시도 · 시군구 · **읍면동까지**. 리는 쓰지 않는다 |
| 정본 | **인구통계(행정동) 기준.** 법정동코드는 이름 검색 보조 |
| ⚠️ 왜 행정동인가 | **k 계산이 인구 교차표를 조회하기 때문이다.** 교차표가 행정동 단위라 법정동 코드로는 조회가 안 된다. 실측(신정현, 2026-08-27) — 신갈동: 행정동 `4146351000` · 법정동 `4146310100`. **시군구는 계층을 헷갈리기 쉽다** — 용인시 `4146000000` · 용인시 기흥구 `4146300000` 이다 |
| 법정동 ↔ 행정동 | **별도 대응표를 둔다. 1:N 을 허용한다** — 한 행정동이 여러 법정동을 덮고 그 반대도 있다 |
| 이름 조회 | `name_index[이름] → 코드 배열`. **단일 값을 반환하지 않는다** |

### 🔵 D 검토 — 동명 지명을 D가 어떻게 고르나

**초안의 빈 곳이다.** `name_index`가 배열을 주는 것은 옳지만, **가명화는 결국 하나를 골라야 한다.** "중앙동"은 전국에 여럿이고, 규칙이 없으면 사람마다 다르게 고른다.

D가 쓸 우선순위를 제안한다.

| 순위 | 규칙 | 근거 |
|---|---|---|
| 1 | **같은 사용자의 다른 지명과 상위 코드를 공유**하는 후보 | 누적·결합이 이 프로젝트의 전제다. 한 사람의 글은 대개 한 생활권이다 |
| 2 | 같은 글 안의 시설이 소속된 행정코드와 일치하는 후보 | `facilities.json`이 있으면 이게 가장 강한 신호다 |
| 3 | **해소되지 않으면 고르지 않는다** — 권역을 빼고 `[특정 동]`, 복원 키에 `"ambiguous": true` | 근거가 없을 때 하나를 고르면 **추측이 확정처럼 전달된다.** 틀린 권역을 붙이는 것보다 안 붙이는 게 낫다 |

> **초안의 3순위(「인구가 가장 많은 후보」)를 뺐다.** 신정현 지적(#5)이 맞다.
>
> 초안은 그 규칙의 근거를 「k를 크게 잡는 쪽 — 위험을 과소평가하지 않는 방향」이라고 적었는데 **방향이 반대다.** k는 조건에 해당하는 인구 수이므로 **k가 크면 특정성이 낮고 위험도 낮게 나온다.** 인구 최대 후보를 고르는 것은 후보 중 **가장 큰 k**를 택하는 것이고, 그건 보수적이 아니라 낙관적이다.
>
> 그 규칙 자체는 최대우도 추정으로는 말이 된다(인구가 많은 곳에 사는 사람이 많으니까). 그러나 **근거를 잘못 적은 게 아니라 자리가 틀렸다** — 근거 없는 추측을 `code`에 넣으면 받는 쪽이 확정값과 구분할 방법이 없다.

### `ambiguous`일 때 무엇을 넘기나

⚠️ **`ambiguous` 가 되는 원인은 둘이다.** 결과는 같지만 원인이 달라 둘 다 적어둔다.

1. **동명 지명** — 「중앙동」이 전국에 여럿이다
2. **법정동 ↔ 행정동 1:N** — 글에 나온 이름이 법정동인데 그것을 덮는 행정동이 여럿이거나, 대응이 확정되지 않는다

둘 다 **후보를 좁히지 못한 것**이므로 처리는 같다 — `code: null` 로 두고 `candidates` 에 행정동 코드 목록을 담는다.

**`code`를 `null`로만 두면 안 된다.** 그러면 C의 k 계산에서 지역 축이 통째로 빠지고, 남는 모집단이 **전국**이 된다 — 가능한 것 중 **가장 큰 과소평가**다. 「중앙동 12곳 중 하나」는 「전국 어딘가」보다 훨씬 좁은 정보다.

그래서 후보 코드를 함께 싣는다.

```json
"restore_key": {
  "code": null,
  "ambiguous": true,
  "candidates": ["4113352500", "4122051000", "4146151000"]
}
```

**k를 어떻게 구할지는 이 계약이 정하지 않는다.** 사실(후보가 이 셋인데 좁히지 못했다)만 전달하고, 처리 규칙은 `specificity.schema.json`이 소유한다. 가명화기가 특정성 엔진의 정책을 지시하면 한쪽만 고쳤을 때 조용히 갈린다.

참고로 판단 재료 하나 — **방어 도구에서는 놓치는 쪽(과소평가)이 헛경보보다 나쁘다.** 사용자가 안전하다고 믿고 아무것도 안 하게 되기 때문이다. 다만 「공격자도 못 좁힌다」고 보면 후보 합집합이 과소평가가 아니라 정확한 값이라는 반론도 성립한다 — 공격자가 우리보다 많은 곁정보를 가질 수 있다고 볼지가 갈림길이다. **C가 정한다.**

## 2. 가명 라벨 형식

| 원 표현 | 축 | kind | 가명 라벨 | 복원 키 |
|---|---|---|---|---|
| 신갈저수지 | location | facility | `[시설A·저수지]` | `{"slot":"A","code":"4146351000"}` |
| 기흥호수 | location | facility | `[시설B·호수]` | `{"slot":"B","code":"4146353000"}` |
| 신갈동 | location | emd | `[경기 남부의 특정 동]` | `{"code":"4146351000"}` |
| 용인시 | location | sigungu | `[경기 남부의 특정 시]` | `{"code":"4146000000"}` |
| 마흔여덟 | age | age_exact | `[40대 후반]` | `{"value":48}` |
| 고1·중2 | family | child_grade | `[중고생 자녀 2명]` | `{"value":["고1","중2"]}` |

**권역 이름**(`경기 남부`)은 시도 + 방위로 고정한다. 시군구 이름을 넣지 않는다.

> **코드 대조 완료 (2026-08-27).**
> 신갈동·용인시는 주민등록 인구통계 자료로 확인했고,
> 기흥호수 및 §1 `candidates` 예시는 행정안전부 `KIKmix.20260701`과
> 2026-07 주민등록 인구통계 자료를 대조하여 행정동 코드로 맞췄다.

### 🔵 D 검토 — 라벨 형식은 정규식으로 못 박는다

2단 모델이 이 라벨을 **읽고 판정**하므로 형식이 흔들리면 판정이 흔들린다. `stage2-io.schema.json`이 이미 `^\[.+\]$`로 검사하고 있으니 여기서 더 좁힌다.

```
[ + 본문 + ]        대괄호는 라벨 경계 전용. 본문에 대괄호를 쓰지 않는다
[시설{슬롯}·{kind}]  시설은 가운뎃점으로 슬롯과 kind를 나눈다
```

원문에 대괄호가 이미 있으면 가명화 전에 전각(`［］`)으로 치환하고 복원 시 되돌린다. **안 그러면 복원 파서가 라벨 경계를 잘못 잡는다.**

## 3. 슬롯 규칙 ⭐

- 슬롯 문자는 **사용자 단위로 유지**한다. 글이 바뀌어도 `신갈저수지 = 시설A`는 그대로다.
- 같은 실제 대상은 항상 같은 슬롯. **이게 깨지면 2단이 "A와 B가 같은 생활권"을 판정할 수 없다.**
- **`user_ref` 단위 결정론적 배정.** 슬롯 테이블을 저장하지 않는다 — 같은 입력이면 같은 슬롯이 다시 나온다. (합의 2026-08-26)

### 🔵 초안의 「세션 안에서만」을 뺀 경위

초안은 「슬롯 테이블은 D가 소유하고, **세션(= 사용자 분석 1회) 안에서만 유효하다**」였다. 이 문장이 위의 「사용자 단위로 유지」와 충돌한다. 세션이 끝나면 테이블이 사라지는데, 같은 사용자가 다음에 다시 분석하면 **`신갈저수지`가 `시설B`가 될 수 있다.** 그러면 —

- 조치 적용 전후를 비교할 수 없다. **추천 엔진이 "이 글 3개를 빼면 79.7 → 41"을 검증하려면 같은 슬롯이어야 한다.**
- 캐시가 무효가 되어 triage 절감률(W8 목표 70%)이 떨어진다.

**합의 — 슬롯을 세션이 아니라 `user_ref` 단위로 결정론적으로 배정한다.**

> 슬롯 = 해당 사용자 글 묶음에서 **행정코드·시설 식별자를 정렬한 순서**대로 A, B, C… 를 부여한다.

테이블을 저장할 필요가 없다. 같은 입력이면 같은 슬롯이 다시 나온다. 글이 추가되면 순서가 밀릴 수 있으므로, **정렬 키는 「첫 등장 글의 `created_at`, 동률이면 행정코드 오름차순」**으로 고정한다. 저장을 안 하므로 §4의 "복원 테이블은 외부로 나가지 않는다"와도 충돌하지 않는다.

## 4. 복원

- 치환 시 **문자 offset을 함께 저장**한다. 문자열 치환만으로 되돌리면 반드시 깨진다.
- 복원 테이블은 **외부로 나가지 않는다.** 외부 LLM에 보내는 것은 가명 텍스트뿐이다 ([RULES-DO-NOT #2](../RULES-DO-NOT.md)).

### 🔵 D 검토 — offset 기준을 명시한다

"문자 offset"만으로는 **어느 텍스트 기준인지**가 빠져 있다. 치환하면 길이가 달라지므로 원문과 가명 텍스트의 offset은 서로 다르다. `stage2-io.schema.json`의 `PseudonymEntry`가 **양쪽을 모두** 담는다.

| 필드 | 기준 | 용도 |
|---|---|---|
| `original.start` / `.end` | **원문** | 복원 |
| `pseudo.start` / `.end` | **가명 텍스트** | 2단 판정 근거를 화면에 하이라이트 |

기준은 **유니코드 코드포인트, 0-based, `[start, end)` 반열림**이다. UTF-16 코드유닛이 아니다 — 이모지·일부 한자가 들어오면 JS와 Python의 인덱스가 갈린다.

#### ⚠️ 오프셋을 세기 전에 **NFC로 정규화**한다

코드포인트를 기준으로 삼는 것만으로는 부족하다. **같은 한글이 두 가지 코드포인트 열로 들어올 수 있다.**

| 정규화 | `신갈동` | |
|---|---|---|
| **NFC** (완성형) | **3** 코드포인트 | 기준 |
| NFD (조합형) | **9** 코드포인트 | 자모가 분리된다 |

**macOS 에서 복사한 텍스트가 실제로 NFD 다.** 정규화하지 않으면 같은 글자에 대해 오프셋이 3배로 벌어지고, `original`·`pseudo`·스팬이 전부 어긋난다. **원인을 찾기 매우 어려운 종류의 버그다** — 화면에는 같은 글자로 보이기 때문이다.

```python
import unicodedata
text = unicodedata.normalize("NFC", raw_text)   # 오프셋을 세기 전에
```

**받는 쪽이 아니라 넣는 쪽에서 한다.** 1단 탐지기(`kopl.c1_span.normalize_nfc`)가 입력을 NFC 로 맞춘 뒤 오프셋을 매기고, 가명화기도 같은 텍스트를 쓴다. 중간에 한 곳이라도 정규화를 건너뛰면 그 지점부터 어긋난다.

> **출처** — 이 항목은 계약에 없던 것이다. 최진필(B)이 1단 골격([#72](../../pull/72))에서 `normalize_nfc` 를 넣은 것을 보고 계약에 올렸다. **계약에 없으면 다음 사람은 안 한다.**

### 🔴 D가 제기하는 결정 사항 — 권역 라벨이 그 자체로 k를 좁힌다

`[경기 남부의 특정 동]`은 **가명이지만 무해하지 않다.** 전국 5,100만에서 수백만으로 이미 좁힌다.

기본 경로(로컬 2단)에서는 문제가 아니다. 판정 정확도에 필요하고 기기 밖으로 나가지 않는다. **외부 LLM 경로(명시적 동의 + 가명화, `plan.md` §4 원칙 2)에서만 문제가 된다.** 계획서가 *"가명화는 면책이 아니라 최소화 조치"* 라고 못박은 지점이 정확히 여기다.

**합의 — 라벨을 두 수준으로 만든다.** (2026-08-26)

| 수준 | 라벨 | 쓰는 곳 |
|---|---|---|
| `L1` (기본) | `[경기 남부의 특정 동]` | **로컬 2단.** 기기 밖으로 안 나감 |
| `L2` (축약) | `[특정 동]` | **외부 LLM 전송 시.** 권역 제거 |

같은 복원 키를 쓰므로 사전은 하나다. 렌더링만 두 갈래다. 동의 경로를 실제로 만들 때(E와) 이 구분이 없으면, 동의만 받고 최소화는 안 한 게 된다.

> **특정성 계산은 `L1` 기준이다** (신정현 확인, 2026-08-26). `L2`는 외부 전송용 표시 형식일 뿐이고, k는 항상 복원 키의 실제 코드로 구한다. **`L2`로 k를 구하면 권역이 빠져 모집단이 부풀고 위험이 과소평가된다.**


즉 **지금은 2명 승인 게이트가 작동하지 않는다.** 혼자 바꿔도 막히지 않는다. 파일 주석이 "역할 확정 + 초대 완료 후 켠다"고 했고 역할은 이미 확정됐으니, 남은 건 **팀원 4명 Collaborator 초대**뿐이다. 초대 없이 실명을 적으면 GitHub가 규칙 전체를 무시한다.

**목요일 계약 4종 머지 전에 초대 → CODEOWNERS 활성화가 끝나야 한다.** 안 그러면 계약을 "게이트"라고 부르면서 실제로는 문서에 불과한 상태로 M2에 들어간다.

`dict_version` 변경 시 재측정 대상에는 **2단 판정 결과도 포함된다** — `stage2-io.schema.json`의 `provenance.dict_version`이 그래서 필수 필드다.

## 9. 가명화기가 내는 것 — `pseudonym_map` ⭐

지금까지 이 문서는 **지명을 무엇으로 바꿀지**만 정했다. 그런데 바꾼 결과를 2단에 넘기려면
**어떤 모양으로 넘길지**도 정해져 있어야 한다. 그 자리가 비어 있었다 —
`stage2-io.schema.json` 의 `PseudonymEntry` 가 유일한 정의인데, 그건 「D 가 받는 모양」이지
「가명화기가 내는 모양」이 아니었다.

> 합의 — **C**(2026-08-27, [#39](../../pull/39)) · 절은 **D** 가 쓴다
> 필드 6개 · offset 기준 §4 그대로 · `ambiguous` 일 때 `candidates` 를 함께 싣는다

### 9-1. 정본은 계약이다

**모양의 정본은 `stage2-io.schema.json` 의 `$defs/PseudonymEntry` 다.** 이 절은 그것을 참조한다.
어긋나면 계약 쪽이 맞다. 여기에 필드를 새로 만들지 않는다.

### 9-2. 치환 1건이 남기는 것

| 필드 | 무엇 | 비고 |
|---|---|---|
| `span_id` | 어느 스팬을 바꿨나 | B 가 준 값을 그대로 |
| `text_id` | offset 이 어느 채널 기준인가 | `body` `title` `profile_bio` `photo_caption:<n>` |
| `label` | 가명 라벨 | §2 형식. `^\[[^\[\]]+\]$` |
| `original` | **원문** 기준 구간 | `{start, end}` |
| `pseudo` | **가명문** 기준 구간 | `{start, end}` |
| `restore_key` | 복원 키 | §2 형식. 축에 따라 채워지는 필드가 다르다 |

**여섯 개 다 필수다.** `additionalProperties` 는 `false` 다 — 임의 필드를 얹으면 검증에서 떨어진다.

**예시 1건**

```json
{
  "span_id": "D01_b04_s01",
  "text_id": "body",
  "label": "[시설A·저수지]",
  "original": { "start": 12, "end": 17 },
  "pseudo":   { "start": 12, "end": 24 },
  "restore_key": { "slot": "A", "code": "4146351000" }
}
```

### 9-3. ⚠️ `original` 과 `pseudo` 를 둘 다 남기는 이유

가명 라벨이 원문과 **글자 수가 다르다.** 위 예시에서 `신갈저수지`(5자)가 `[시설A·저수지]`(9자)로
바뀌면서 그 뒤의 모든 스팬 offset 이 4칸씩 밀린다.

```
원문   집에서 십 분이면 닿는 신갈저수지라 새벽에 자주 간다
                          ^^^^^ 12–17

가명문 집에서 십 분이면 닿는 [시설A·저수지]라 새벽에 자주 간다
                          ^^^^^^^^^ 12–24
```

**원문 offset 만 남기면** 가명문에서 그 자리를 못 찾는다.
**가명문 offset 만 남기면** 복원할 자리를 못 찾는다. 둘 다 필요하다.

offset 기준은 §4 그대로다 — **유니코드 코드포인트**, 0-based, `[start, end)` 반열림.

### 9-4. ⚠️ 대괄호는 라벨 경계 전용

원문에 `[` 나 `]` 가 있으면 **가명화 전에** 전각(`［ ］`)으로 치환하고 복원할 때 되돌린다.
안 그러면 복원 파서가 라벨 경계를 잘못 잡는다 (§2).

### 9-5. 좁히지 못했을 때 — `candidates`

동명 지명을 하나로 못 좁히면 `ambiguous: true` 로 내고, **`code` 는 `null`, `candidates` 에 후보를 담는다.**

```json
{
  "restore_key": {
    "ambiguous": true,
    "code": null,
    "candidates": ["4146351000", "4113510300", "2817710200"]
  }
}
```

**`candidates` 를 빼면 안 되는 이유** — `code: null` 만 주면 지역 축이 k 계산에서 **통째로 빠져
모집단이 전국이 된다.** 가능한 것 중 가장 큰 과소평가다. 「중앙동 12곳 중 하나」는
「전국 어딘가」보다 훨씬 좁은 정보이므로 버리지 않는다.

⚠️ **이 값을 k 계산에서 어떻게 다룰지는 여기서 정하지 않는다.** 사실만 넘기고 처리 규칙은
`specificity.schema.json`(C)이 소유한다. 가명화기가 특정성 엔진의 정책을 지시하면
한쪽만 고쳤을 때 조용히 갈린다.

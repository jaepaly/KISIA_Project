## 0. 한 장 요약

| 항목 | 확정 |
|---|---|
| 주 지표 | partial match — `type` 일치 + **IoU ≥ 0.5** |
| 지표 분해 | `type` · `level` · `subject`를 **각각 따로** 산출. 합산 금지 |
| 스팬 유형 | **10개** (상한) |
| 스팬 필드 | `start` `end` `text` `type` `level` `subject` — **6개까지** |
| 위치 단위 | **문자 offset**, `start` 포함 / `end` 미포함, **NFC** |
| 경계 | **어절 정렬**, 끝 어절의 조사·어미 포함, 용언 제외 |
| 겹침 | **금지 · 최장 우선** |
| BIO 밖 | 밈·유행어, 세대 신호 — 글 단위 플래그 |
| `score` | 모델 출력 전용 `[0,1]`. **계약에 임계값을 두지 않는다** |
| 라벨 금지 | 학력 · 학교 · 전공 · 정치성향 · 건강 · 지적 수준 |

## 1. 이 문서가 정하는 것

합성 코퍼스의 **정답표를 어떻게 적을지**에 대한 약속이다. 이 문서가 확정되어야
① A가 골드셋을 매길 수 있고 ② B가 `span.schema.json`을 쓸 수 있고 ③ E가 계약 4종을 머지할 수 있다.

이 문서가 정하지 **않는** 것: 위험도 계산(C), 종합 판정(D), 화면 표기(E).

### 1-1. 설계 메타와 판독 라벨은 다른 층위다

인물 JSON의 `clue_plan`과 이 문서의 스팬 라벨은 이름이 겹치는 필드가 있지만 **서로 다른 것**이다.

| | 뜻 | 누가 쓰나 |
|---|---|---|
| `clue_plan.subject` `clue_plan.level` | **설계자가 의도한** 값 | A (인물 설계 시) |
| 스팬 `subject` `level` | **문장만 보고 판독한** 값 | 라벨러 · 교사 LLM · 1단 모델 |

설계자는 항상 단서의 소유자를 알기 때문에 `clue_plan.subject`에는 구조적으로 `unknown`이 나오지 않는다.
**두 값이 달라도 된다.** 설계 의도는 `self`인데 문장이 애매해 판독은 `unknown`이 나오는 표본이 오히려 필요하다(§9-2).

## 2. 채점 기준 ⭐ — 다른 모든 규칙이 여기 묶인다

### 2-1. 왜 이게 맨 앞에 오나

**스팬 탐지 F1 ≥ 0.80은 [필수] 지표다.** 그런데 같은 예측에 대해 exact match F1과 partial match F1은 완전히 다른 숫자가 나온다. 기준을 안 정하면 W1에 선언한 숫자와 W7에 재는 숫자가 다른 것이 된다.

그리고 이 결정 하나에 셋이 매달려 있다.

| 묶여 있는 것 | 어떻게 |
|---|---|
| **W3 IAA** | 사람 둘의 일치도도 **같은 기준**으로 재야 한다. 다르면 "IAA의 80%"라는 목표 산식이 성립하지 않는다 |
| **스팬 경계 규칙**(§5) | exact면 조사 하나에 F1이 흔들리고, partial이면 경계가 훨씬 덜 중요해진다 |
| **G2 지표 갱신**(W4) | 여기서 기준이 바뀌면 W1 선언치와 비교가 불가능해진다 |

### 2-2. 확정

> **주 지표 = partial match. `type`이 같고 IoU ≥ 0.5이면 정답.**

```
IoU = |예측 ∩ 정답| / |예측 ∪ 정답|          # 문자 수 기준
```

| 항목 | 확정 |
|---|---|
| 유형 | `type`이 **완전히 일치**해야 한다. 부분 점수 없음 |
| 경계 | **IoU ≥ 0.5** |
| 매칭 | **1:1.** 한 정답에 여러 예측이 걸리면 IoU 최대 하나만 정답, 나머지는 오탐 |
| 참고치 | **exact match F1을 함께 기록한다** (경계 품질이 나빠지는 걸 놓치지 않기 위해) |

**왜 IoU인가.** 정답 길이만 분모로 쓰면(`|∩| / |정답|`) **아주 긴 스팬을 뱉어 점수를 딸 수 있다.** 문장 전체를 `LOC_FACILITY`로 잡아도 정답을 덮으므로 1.0이 나온다. IoU는 양쪽을 다 보므로 이게 막힌다.

### 2-3. 합산 지표를 만들지 않는다

`type` · `level` · `subject`는 **각각 따로 낸다.** 하나의 종합 점수로 합치지 않는다.

| 무엇 | 어떻게 |
|---|---|
| `type` + 경계 | 스팬 F1 — **[필수] 지표는 이것 하나** |
| `level` | `type` 정답인 스팬에 한해 등급 일치율 |
| `subject` | `type` 정답인 스팬에 한해 귀속 정확도 |

섞으면 탐지 성능과 귀속 판정이 한 숫자에 묻힌다. 어느 쪽이 나빠서 점수가 떨어졌는지 알 수 없으면 고칠 수가 없다.

`level`별 F1 분해(명시/암묵)도 같은 원칙에서 따로 낸다.

**모든 수치에는 측정일 · 코퍼스 버전 · 모델 버전을 함께 적는다** (RULES-DO-NOT #9).

## 3. 스팬 유형 목록

### 3-1. 유형 예산 — 먼저 상한부터

유형을 늘리면 라벨이 `2n+1`개로 늘고, **유형당 골드셋 스팬 수가 그만큼 줄어든다.**

| 유형 수 | BIO 라벨 수 | 유형당 골드셋 스팬 (600~700 기준) |
|---|---|---|
| 8 | 17 | 75~88 |
| **10** | **21** | **60~70** |
| 14 | 29 | 43~50 |
| 20 | 41 | 30~35 ← 유형별 F1이 의미를 잃는다 |

유형별 F1을 내려면 유형당 최소 30~50 스팬이 필요하다. **상한을 10개로 잡는다.**
쪼개고 싶은 충동이 들면 유형이 아니라 `level`(등급)이나 `subject`로 구분되는지 먼저 본다.

> ⚠️ **위 표는 균등 분포를 가정한 평균이다.** 실제로는 `LOC_FACILITY`·`AGE`에 몰리고 `SEX`·`INCOME`·`REL_WORK`는 30개도 안 나올 수 있다. 그러면 그 유형의 F1이 무의미해진다 — **대응은 §9.**

### 3-2. 확정 — 10개

7속성(`age` `sex` `location` `occupation` `family` `commute` `income`)에서 유도했다.

| 유형 | 무엇을 잡나 | 예 | 기여 속성 |
|---|---|---|---|
| `AGE` | 나이·연령대 신호 | 마흔여덟 / 서른넷 / 90년생 | age |
| `SEX` | 성별 신호 | 아내가 / 남편이 / 와이프 | **sex, family** |
| `LOC_ADMIN` | 행정구역명 | 성수동 / 용인 / 기흥 | location |
| `LOC_FACILITY` | 시설·랜드마크·상호 | 신갈저수지 / 서울숲 / 성수역 | location |
| `REL_HOME` | 거주 관계어 | 집 근처 / 집 앞 / 동네 / 우리 동네 | location |
| `REL_WORK` | 직장 관계어 | 회사 앞 / 사무실 근처 / 공장에서 | occupation, commute |
| `JOB` | 직업·직무·업종 | 생산관리 / 완성차 공장 / 카페 매니저 | occupation, income |
| `FAM` | 가족 구성·생애단계 | 첫째가 고등학교 배정 / 손주 돌잔치 | family, age |
| `COMMUTE` | 교통수단·노선·통근 패턴·**통근 관계어** | 2호선 / 자차 출퇴근 / 퇴근길 | commute, location |
| `INCOME` | 소비·지출 수준 신호 | 장비 값 / 회비 / 등급제 | income |

> **유형과 속성은 1:1이 아니다.** `FAM` 스팬 하나("첫째가 고등학교 배정")가 `family`와 `age`를 동시에 드러낸다.
> 그래서 **속성 매핑은 이 표에만 두고, 스팬 레코드에는 넣지 않는다.** 어느 속성으로 이어지는지는 C가 계산한다.

**배우자 호칭("남편", "아내", "와이프")은 `SEX`로 잡는다.** 화자의 성별과 배우자의 존재를 동시에 드러내므로 기여 속성이 `sex`·`family` 둘이다.
한 스팬에 유형을 둘 붙일 수는 없으므로(§6), 유형은 `SEX` 하나로 두고 **`family` 도출은 매핑표를 통해 C가 한다.**

### 3-3. 관계어를 왜 둘로 쪼갰나

**같은 시설이 다른 축을 좁히기 때문이다.**

```
집 근처   신갈저수지   → 거주지 축
회사 앞   신갈저수지   → 직장·통근 축
```

하나로 묶으면 C가 그 시설을 어느 축에 붙일지 판단할 근거가 사라진다. **그 판단이 곧 특정성 엔진의 입력**이고, R1에서 "동탄 사는 지인"을 걸러낸 것도 결국 이 구분이다.

라벨러 관점에서도 갈릴 여지가 적다 — `집 / 동네 / 우리 동네` → `REL_HOME`, `회사 / 사무실 / 공장` → `REL_WORK`.

**통근 관계어("퇴근길", "출근하다가")는 `COMMUTE`가 흡수한다.** 관계어를 셋으로 쪼개면 예산을 넘는다.

## 4. 스팬에 붙는 세 가지

### 4-1. `level` — 단서 등급

> **정의: `level`은 그 스팬이 *단독으로* 속성을 얼마나 확정하는가를 뜻한다.**
> 다른 스팬과의 조합 효과는 여기서 다루지 않는다 — 그건 C가 계산한다.

이 정의가 없으면 "집 근처"와 "신갈저수지"에 각각 무엇을 붙일지 답이 나오지 않는다.

| 등급 | 뜻 | 예 | 왜 |
|---|---|---|---|
| `explicit` | 값이 그대로 적힘 | 마흔여덟 / 2호선 | 단독으로 값이 나온다 |
| `implicit` | 값이 직접 안 적혔으나 문맥상 거의 확정 | 완성차 공장 출장 / 원두 발주 | 단독으로 업종이 거의 확정된다 |
| `inferential` | 단독으로는 미확정 | 신갈저수지 / 집 근처 | 다른 스팬과 묶여야 좁혀진다 |

등급은 **스팬마다 하나** 부여하고, 전 스팬에 예외 없이 붙인다.

**표기 형식은 등급과 무관하다.** `34살`과 `서른넷`, `마흔여덟`은 전부 `explicit`이다.
아라비아 숫자냐 한글 수사냐는 *기존 도구가 잡느냐*의 문제이지 *값이 적혀 있느냐*의 문제가 아니다.

> ⚠️ **B의 탐지 도구 비교 문서에서 한글 수사 나이 표현을 "암묵"으로 부르고 있다면 용어를 정렬해야 한다.**
> 이 스키마 기준으로 "마흔여덟"은 `explicit`이며, **기존 도구가 못 잡는 explicit**이다.
> 그 결과 explicit F1 ≥ 0.80은 당초 예상보다 어려운 목표가 된다 — 사전·정규식 기반 도구가 한글 수사를 놓치기 때문이다. **목표치 유지 여부는 B가 판단한다.**

> ⚠️ **암묵-only ablation이 이 필드 위에서 재현된다.** 명시 단서 글을 제외해도 7속성이 유지되는지가 프로젝트 전제인데, `level` 정의가 흔들리면 *무엇을 제외한 실험인지*가 흔들린다.

### 4-2. `subject` — 누구의 정보인가

코퍼스 설계상 **오답 유도용 함정**을 심는다. "동탄 사는 친구랑 밤낚시"의 `동탄`은 본인 거주지가 아니다.

| 값 | 언제 |
|---|---|
| `self` | 기본. 문장이 타인 소유임을 밝히지 않았다 |
| `other` | 문장이 **명시적으로** 타인에게 귀속시켰다 — "친구가", "지인이", "옆집" |
| `unknown` | 문장만으로 판단 불가 |

**왜 필드를 하나 더 늘리면서까지 넣나 — 세 가지다.**

1. **함정 판별이 기존 도구와 갈리는 가시적 지점이다.** 지명이 나오면 무조건 거주지로 찍는 사전 기반 도구와 여기서 갈린다. `subject`가 없으면 *"동탄을 걸러냈다"*를 정량화할 방법이 없고, 「기존 도구 대비 추가 탐지율」의 질적 근거도 사라진다.
2. **제3자·미성년 정보 표시를 겸한다.** 셰어런팅 단서(자녀 정보)가 `other`로 잡힌다. 멘토 피드백에 미결로 올라 있는 항목이다.
3. **`risk`와 달리 일관 라벨이 된다.** `subject`는 **문장이 국소적으로** 말해준다(누구 것이라고 문장에 적혀 있나). `risk`는 글 전체를 봐야 한다. 그래서 하나는 라벨이 되고 하나는 안 된다.

> ⚠️ **`unknown`은 쓰레기통이 되기 쉽다.** *"문장만으로 판단 불가"*일 때만 쓴다. `unknown` 표본을 어떻게 확보하고 얼마나 둘지는 §9-2.

### 4-3. `type`

§3-2의 10개 중 하나. 부분 점수는 없다(§2-2).

## 5. 위치 표기와 경계

### 5-1. 좌표

| 항목 | 확정 |
|---|---|
| 단위 | **문자 offset** (토큰 인덱스·바이트 아님) |
| 구간 | `start` **포함** / `end` **미포함** — 파이썬 슬라이스와 동일 |
| 정규화 | 본문·라벨 모두 **NFC**로 정규화한다 |
| 검증 | `text == body[start:end]` 가 항상 참이어야 한다 |

문자 offset을 쓰는 이유: **토크나이저는 바뀌지만 코퍼스는 살아남는다.**
`end` 포함/미포함을 안 정하면 **전 코퍼스가 한 글자씩 어긋난다.**

**NFC를 명시하는 이유**: 한글이 NFD(자모 분리)로 저장되면 "성수동"이 3자가 아니라 8자로 세어진다. 팀에 Windows·macOS가 섞여 있으면 같은 본문에 대해 사람마다 다른 offset이 나온다. 생성·라벨·검증 전 단계에서 NFC를 강제한다.

### 5-2. 경계 — 어절에 정렬한다

> **스팬은 단서를 이루는 명사구를 감싸되, 경계는 어절(공백)에 정렬한다.**
> **끝 어절의 조사·어미는 포함한다. 용언(서술어)은 제외한다.**

```
"첫째가 고등학교 배정 받았습니다"

✗ (4,11) "고등학교 배정"        ← 조사를 떼려다 스팬이 둘로 쪼개진다 = 최장 우선과 충돌
✗ (0,16) "첫째가 고등학교 배정 받았습니다"  ← 서술어까지 삼켰다
○ (0,11) "첫째가 고등학교 배정"
```

**조사를 떼는 판단이 IAA를 가장 많이 깎는 지점인데, 얻는 게 없다.** §2의 partial match와 짝을 이루면 조사 한두 글자는 F1에 영향을 주지 않는다. `text == body[start:end]` 검증도 어절 정렬이 훨씬 안전하다.

## 6. 겹침 규칙

> **겹침 금지 · 최장 우선.**

BIO 태깅은 토큰 하나에 라벨 하나만 붙일 수 있어 겹치는 스팬을 표현하지 못한다.
이건 취향이 아니라 **모델 구조에서 나오는 제약**이다. 계약이 겹침을 허용하면 코퍼스를 전부 다시 라벨해야 한다.

```
"집 근처라 자주 가는 신갈저수지"

✗ (0,17) 전체를 거주 단서로  +  (12,17) 신갈저수지를 시설로   ← 겹침, 표현 불가
○ (0,4)  집 근처   → REL_HOME       / inferential / self
  (12,17) 신갈저수지 → LOC_FACILITY  / inferential / self     ← 두 스팬으로 분리
```

관계어를 별도 유형으로 둔 이유가 이것이다. 붙여 잡으면 겹침이 생기고, 안 잡으면 "집 근처"가 사라진다.

**한 스팬이 여러 속성을 시사해도 유형은 하나만 붙인다.** 파생 속성은 §3-2 매핑표를 거쳐 C가 계산한다.

---

## 7. BIO 밖에 두는 것 — 별도 레이어 2종

**스팬으로 잡지 않지만 버리지도 않는다.** 글 단위 플래그로 남긴다.

| 레이어 | 무엇 | 왜 BIO 밖인가 | 채점 | 기록 |
|---|---|---|---|---|
| **밈·유행어** | 손민수 / 정병 / 에바 | 계획서 설계원칙 4 — *"밈은 모델이 아니라 사전. 파일 교체로 갱신, 재학습 불필요."* **태그셋에 넣으면 모델이 밈을 외우고 그 성질이 사라진다** | 사전 재현율·오탐률 | `flags.meme_hits` |
| **세대 신호** | "무릎이 예전 같지 않네요" | 라벨러가 가장 많이 갈리는 표현이다. **B의 암묵 F1 목표치가 IAA에 묶여 있으므로, 갈리는 항목을 스팬에 넣으면 목표치가 같이 깎인다** | 글 단위 플래그 정확도 | `flags.gen_signal` |

밈 사전은 B 소유 `data/dict/signatures/meme.json`.

**세대 신호를 빼도 잃는 게 없다.** 계획서 §4가 1단의 일을 *"준식별자 스팬 탐지(BIO) · **문체/세대 신호** · 밈 사전 매칭"* 셋으로 이미 나눠뒀다. 스팬에서 빼도 2단은 그 문장을 그대로 보므로 나이 추론 근거로 계속 쓰인다 — 선행 PoC에서 이 표현이 근거로 잡힌 것도 2단 판정에서였다.

그리고 **경계를 정할 필요 자체가 사라진다** (*"무릎이"*부터인가 *"않네요"*까지인가).

## 8. 레코드 형식

### 8-1. 스팬

```json
{"start": 12, "end": 17, "text": "신갈저수지",
 "type": "LOC_FACILITY", "level": "inferential", "subject": "self"}
```

**스팬에 붙는 필드는 위 6개까지.**

| 넣지 않는 필드 | 이유 |
|---|---|
| `risk` `severity` | 같은 표현의 위험도가 문맥마다 다르다. 일관 라벨이 불가능 → C가 계산 |
| `attr` | 유형-속성이 1:n이다. §3-2 매핑표로 대신한다 |

### 8-2. `score` — 모델 출력에만 붙는다

B의 1단 모델 출력에는 `score`가 추가된다. **모델 확률값이며 위험도가 아니다.**

| 항목 | 확정 |
|---|---|
| 범위 | `[0, 1]` 실수 |
| 골드셋 | **없다.** 사람이 매긴 라벨에는 `score`를 붙이지 않는다 |
| 임계값 | **계약에 두지 않는다** |

**임계값을 계약에 박지 않는 이유.** 임계값은 실험으로 정해지는 값이고 데이터가 바뀌면 같이 움직인다. 계약에 숫자를 박으면 조정할 때마다 **승인 2명**을 받아야 하고, 그러면 아무도 조정하지 않게 된다.

임계값은 `experiments/`에서 정하고 **측정일 · 코퍼스 버전 · 모델 버전과 함께 기록한다**(RULES-DO-NOT #9). 실험 전 잠정 운영값이 필요하면 실험 문서 쪽에 두고, 이 계약은 건드리지 않는다.

### 8-3. 글

```json
{"post_id": "S01_b07", "persona_id": "S01",
 "spans": [ ... ],
 "flags": {"gen_signal": true, "meme_hits": [], "negative_control": false},
 "reviewed": true}
```

| 필드 | 뜻 |
|---|---|
| `gen_signal` | 세대 신호 표현이 있는가 (§7) |
| `meme_hits` | 매칭된 밈 표제어 배열. 없으면 `[]` (§7) |
| `negative_control` | 단서를 의도적으로 넣지 않은 글인가 |
| `reviewed` | **라벨러가 이 글을 실제로 검토했는가** |

**`reviewed`가 있어야 `spans: []`의 뜻이 확정된다.** 빈 배열이 "제대로 매겨서 0개"인지 "아직 안 매김"인지 구분할 방법이 없으면, 코퍼스의 10~15%를 차지하는 네거티브 글 전체가 검증 불가가 된다.

### 8-4. `schema_version`

**jsonl 파일의 첫 줄에 헤더 레코드로 한 번 둔다.** 스팬마다 붙이지 않는다.

```json
{"schema_version": "1.0", "corpus_version": "v0", "created": "2026-08-25"}
```

계약 4종 전부에 `schema_version`이 들어가기로 되어 있고, 라벨 파일은 이 형태가 가장 싸다.

### 8-5. 골드셋 파일 경로

```
data/corpus/v0/gold/<persona_id>_spans.jsonl        예: S01_spans.jsonl
```

**인물 단위로 나눈다.** 생성 산출물이 이미 인물 단위(`data/corpus/v0/posts/S01.jsonl`)라 1:1로 대응시키면 병합·재생성·부분 재라벨이 전부 파일 하나 단위로 끝난다. 작업자 이니셜로 나누면 인물이 여러 파일에 흩어져 재생성 때 추적이 어렵다.

## 9. 분포는 생성 단계에서 통제한다 (A)

### 9-1. 희소 유형 할당량

§3-1의 "유형당 60~70 스팬"은 균등 분포일 때의 평균이다. 실제로는 `SEX`·`INCOME`·`REL_WORK`가 30개도 안 나올 수 있고, **그러면 그 유형의 F1이 무의미해지고 §3-1 예산표의 논거가 사후에 무너진다.**

**이 분포를 통제할 수 있는 사람은 A뿐이다** — 인물 JSON의 `clue_plan`이 어떤 유형이 몇 번 등장할지를 결정하기 때문이다. 코퍼스가 동결된 뒤에 세어보고 메우려면 늦는다.

> **인물 JSON 작성 규칙**: 인물 5명 묶음마다 `INCOME` · `SEX` · `REL_WORK` 단서를 **각 2건 이상** 배치한다.

이 할당량은 **인물 5명분 단서 예산의 약 20%를 미리 묶는다.** 나중에 끼워 넣는 게 아니라 인물 설계 시점에 배정해야 노이즈 비율이 깨지지 않는다.

> ⚠️ **`INCOME`은 생성 프롬프트와 충돌한다.** 리얼리즘 확보를 위해 실명 브랜드·상호를 금지하고 있는데, 소비 수준 신호는 상당 부분 브랜드로 표현된다. 금액·등급·빈도 등 브랜드가 아닌 표현으로 단서를 설계해야 한다.

### 9-2. `unknown` 표본 확보

`subject` 귀속 정확도(§2-3)를 재려면 `unknown` 판독이 실제로 나오는 문장이 코퍼스에 있어야 한다. 없으면 세 값 중 하나가 한 번도 시험되지 않는다.

**설계자는 소유자를 알기 때문에(§1-1) `unknown`을 의도할 수 없다.** 대신 **귀속을 드러내는 표지를 문장에서 뺀 단서**를 설계한다.

> **인물 JSON 작성 규칙**: `clue_plan` 항목에 `ambiguous: true` 플래그를 둔다.
> **인물 5명 묶음마다 2건 이상.** 설계 의도(`subject`)는 `self`/`other` 그대로 두고, 문장만 귀속이 드러나지 않게 쓴다.

**새 단서를 추가하는 게 아니라 기존 단서에 플래그를 붙이는 것이다.** 그래서 단서 편수가 늘지 않고 **노이즈 비율(70~80%)이 영향받지 않는다.**

| 항목 | 확정 |
|---|---|
| 목표 규모 | 골드셋 `unknown` 스팬 **30건 이상** — §3-1·§9-1의 "유형당 30건" 기준과 동일 |
| 배정 | 인물 5명 묶음마다 2건 이상 (인물 100명 기준 약 40건) |
| 비용 | 없음. 기존 단서에 플래그를 붙이는 방식 |

**어떤 단서가 `ambiguous` 후보인가.** 귀속 표지("친구가", "집 앞", "우리")가 문장에 없어야 한다. `REL_HOME` 같은 관계어는 그 자체가 귀속 표지라 후보가 되지 않는다. `FAM`·`JOB`처럼 **소유자를 밝히지 않고도 자연스러운 유형**이 적합하다.

판독이 실제로 `unknown`으로 갈리는지는 W3 골드셋 검수에서 확인하고, 30건에 못 미치면 그때 추가 배정한다.

### 9-3. 사후 확인

W3 골드셋 검수 시 **유형별 스팬 수와 `subject` 값 분포를 세어 `experiments/`에 기록한다.**
30건 미만인 유형은 **F1을 내지 않고 "표본 부족"으로 표기**한다. `subject`도 같다.

## 10. 라벨하지 않는 것

**학력 · 학교 · 전공 · 정치성향 · 건강 · 지적 수준**은 유형 목록에 넣지 않는다.
방어 도구가 민감 속성 추론을 학습하면 그 자체가 무기가 된다.

**`type` enum에 이것들이 없다는 사실 자체가 RULES-DO-NOT #4의 강제 장치다.** 문서에 적어둔 규칙은 잊히지만 enum에 없는 값은 검사기가 잡는다.

---

## 11. 검사기가 강제할 것

`span.schema.json`과 검증 스크립트가 기계적으로 잡아야 하는 항목이다. **문서에만 적힌 규칙은 지켜지지 않는다.**

| # | 규칙 | 근거 | 검사기 |
|---|---|---|---|
| 1 | `type` ∈ 10개 enum | §3-2 · §10 | 라벨 |
| 2 | `level` ∈ `explicit` `implicit` `inferential` | §4-1 | 라벨 |
| 3 | `subject` ∈ `self` `other` `unknown` | §4-2 | 라벨 |
| 4 | `text == body[start:end]` | §5-1 | 라벨 |
| 5 | 본문·`text` 모두 NFC | §5-1 | 라벨 · 생성 |
| 6 | `0 ≤ start < end ≤ len(body)` | §5-1 | 라벨 |
| 7 | 한 글 안에서 스팬 구간이 겹치지 않음 | §6 | 라벨 |
| 8 | 스팬 필드가 6개 외에 없음 (모델 출력만 `score` 허용) | §8-1 · §8-2 | 라벨 |
| 9 | `score` ∈ `[0,1]`, 골드셋에는 없음 | §8-2 | 라벨 |
| 10 | 파일 첫 줄에 `schema_version` 헤더 | §8-4 | 라벨 |
| 11 | `spans: []`인 글에 `reviewed`가 있음 | §8-3 | 라벨 |
| 12 | 인물 5명 묶음마다 `INCOME`·`SEX`·`REL_WORK` 각 2건 이상 | §9-1 | 인물 JSON |
| 13 | 인물 5명 묶음마다 `ambiguous` 2건 이상 | §9-2 | 인물 JSON |

12·13번은 인물 JSON 검증기(`validate.py`)가, 나머지는 라벨 검증기가 맡는다.

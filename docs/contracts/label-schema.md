## v0.1 → v0.2 변경 요약

> **B는 이 표만 봐도 된다.** 아래 6건이 v0.1의 미결 5건을 닫은 결과이고, 나머지는 문구 정리다.

| # | 변경 | 근거 |
|---|---|---|
| 1 | **채점 기준 신설**(§2) — partial match(type 일치 + IoU ≥ 0.5), exact는 참고치 | 스팬 F1 ≥ 0.80이 [필수] 지표인데 기준이 없었다. IAA·경계 규칙이 전부 여기 묶인다 |
| 2 | **스팬 경계 = 어절 정렬**(§5) — 끝 어절의 조사·어미 포함 | v0.1의 "조사 제외"안은 §6 최장 우선과 충돌했다. 조사 판단은 IAA만 깎고 얻는 게 없다 |
| 3 | `MEME_GEN` · 신체 노화 표현을 **BIO 밖 별도 레이어로**(§7) | 밈을 태그셋에 넣으면 모델이 밈을 외운다 — 계획서 설계원칙 4(사전으로 갱신, 재학습 불필요)가 깨진다 |
| 4 | 그 칸으로 `REL_ANCHOR` → **`REL_HOME` / `REL_WORK` 분리**(§3) | 같은 시설이 거주 축을 좁히는지 직장 축을 좁히는지가 갈린다. 그 판단이 C의 입력이다 |
| 5 | **`subject: self / other / unknown` 추가**(§4) | 함정("동탄 사는 친구")을 표시할 자리가 없었다. 제3자·미성년 정보 표시도 겸한다 |
| 6 | **`level` 정의 명문화**(§4) — "그 스팬이 **단독으로** 갖는 확정력" | v0.1 예시가 두 스팬의 조합이라 스팬 단위 규칙과 어긋났다 |

**부록 샘플 5개 → 8개.** 네거티브 2문장과 희소 유형(`SEX`·`INCOME`) 1문장을 추가했다.

## 1. 이 문서가 정하는 것

합성 코퍼스의 **정답표를 어떻게 적을지**에 대한 약속이다. 이 문서가 확정되어야
① A가 골드셋을 매길 수 있고 ② B가 `span.schema.json`을 쓸 수 있고 ③ E가 목요일에 계약 4종을 머지할 수 있다.

이 문서가 정하지 **않는** 것: 위험도 계산(C), 종합 판정(D), 화면 표기(E).

## 2. 채점 기준 ⭐ — 다른 모든 규칙이 여기 묶인다

### 2-1. 왜 이게 맨 앞에 오나

**스팬 탐지 F1 ≥ 0.80은 [필수] 지표다.** 그런데 같은 예측에 대해 exact match F1과 partial match F1은 완전히 다른 숫자가 나온다. 기준을 안 정하면 W1에 선언한 숫자와 W7에 재는 숫자가 다른 것이 된다.

그리고 이 결정 하나에 셋이 매달려 있다.

| 묶여 있는 것 | 어떻게 |
|---|---|
| **W3 IAA 파일럿** | 사람 둘의 일치도도 **같은 기준**으로 재야 한다. 다르면 "IAA의 80%"라는 목표 산식이 성립하지 않는다 |
| **스팬 경계 규칙**(§5) | exact면 조사 하나에 F1이 흔들리고, partial이면 경계가 훨씬 덜 중요해진다 |
| **G2 지표 갱신**(W4) | 여기서 기준이 바뀌면 W1 선언치와 비교가 불가능해진다 |

### 2-2. 확정

> **주 지표 = partial match. `type`이 같고 IoU ≥ 0.5이면 정답.**

```
IoU = |예측 ∩ 정답| / |예측 ∪ 정답|          # 문자 수 기준
```

| 항목 | 확정 |
|---|---|
| 유형 | `type`이 **완전히 일치**해야 한다. 부분 점수 없음 |
| 경계 | **IoU ≥ 0.5** |
| 매칭 | **1:1.** 한 정답에 여러 예측이 걸리면 IoU 최대 하나만 정답, 나머지는 오탐 |
| 참고치 | **exact match F1을 함께 기록한다** (경계 품질이 나빠지는 걸 놓치지 않기 위해) |
| 등급별 분해 | `level`별로 따로 낸다 — 명시/암묵 F1이 별개 지표다 |

**왜 IoU인가.** 정답 길이만 분모로 쓰면(`|∩| / |정답|`) **아주 긴 스팬을 뱉어 점수를 딸 수 있다.** 문장 전체를 `LOC_FACILITY`로 잡아도 정답을 덮으므로 1.0이 나온다. IoU는 양쪽을 다 보므로 이게 막힌다.

**`subject`(§4)는 F1에 넣지 않는다.** 별도로 정확도를 낸다 — 섞으면 탐지 성능과 귀속 판정이 한 숫자에 묻힌다.

## 3. 스팬 유형 목록

### 3-1. 유형 예산 — 먼저 상한부터

유형을 늘리면 라벨이 `2n+1`개로 늘고, **유형당 골드셋 스팬 수가 그만큼 줄어든다.**

| 유형 수 | BIO 라벨 수 | 유형당 골드셋 스팬 (600~700 기준) |
|---|---|---|
| 8 | 17 | 75~88 |
| **10** | **21** | **60~70** |
| 14 | 29 | 43~50 |
| 20 | 41 | 30~35 ← 유형별 F1이 의미를 잃는다 |

유형별 F1을 내려면 유형당 최소 30~50 스팬이 필요하다. **상한을 10개로 잡는다.**
쪼개고 싶은 충동이 들면 유형이 아니라 `level`(등급)이나 `subject`로 구분되는지 먼저 본다.

> ⚠️ **위 표는 균등 분포를 가정한 평균이다.** 실제로는 `LOC_FACILITY`·`AGE`에 몰리고 `SEX`·`INCOME`·`REL_WORK`는 30개도 안 나올 수 있다. 그러면 그 유형의 F1이 무의미해진다 — **대응은 §9.**

### 3-2. 확정 — 10개

7속성(`age` `sex` `location` `occupation` `family` `commute` `income`)에서 유도했다.

| 유형 | 무엇을 잡나 | 예 | 기여 속성 |
|---|---|---|---|
| `AGE` | 나이·연령대 신호 | 마흔여덟 / 서른넷 / 90년생 | age |
| `SEX` | 성별 신호 | 아내가 / 남편이 / 와이프 | sex |
| `LOC_ADMIN` | 행정구역명 | 성수동 / 용인 / 기흥 | location |
| `LOC_FACILITY` | 시설·랜드마크·상호 | 신갈저수지 / 서울숲 / 성수역 | location |
| **`REL_HOME`** | **거주 관계어** | 집 근처 / 집 앞 / 동네 / 우리 동네 | location |
| **`REL_WORK`** | **직장 관계어** | 회사 앞 / 사무실 근처 / 공장에서 | occupation, commute |
| `JOB` | 직업·직무·업종 | 생산관리 / 완성차 공장 / 카페 매니저 | occupation, income |
| `FAM` | 가족 구성·생애단계 | 첫째가 고등학교 배정 / 손주 돌잔치 | family, age |
| `COMMUTE` | 교통수단·노선·통근 패턴·**통근 관계어** | 2호선 / 자차 출퇴근 / 퇴근길 | commute, location |
| `INCOME` | 소비·지출 수준 신호 | 장비 값 / 회비 / 브랜드 | income |

> **유형과 속성은 1:1이 아니다.** `FAM` 스팬 하나("첫째가 고등학교 배정")가 `family`와 `age`를 동시에 드러낸다.
> 그래서 **속성 매핑은 이 표에만 두고, 스팬 레코드에는 넣지 않는다.** 어느 속성으로 이어지는지는 C가 계산한다.

### 3-3. 관계어를 왜 둘로 쪼갰나

**같은 시설이 다른 축을 좁히기 때문이다.**

```
집 근처   신갈저수지   → 거주지 축
회사 앞   신갈저수지   → 직장·통근 축
```

하나로 묶으면 C가 그 시설을 어느 축에 붙일지 판단할 근거가 사라진다. **그 판단이 곧 특정성 엔진의 입력**이고, R1에서 "동탄 사는 지인"을 걸러낸 것도 결국 이 구분이다.

라벨러 관점에서도 갈릴 여지가 적다 — `집 / 동네 / 우리 동네` → `REL_HOME`, `회사 / 사무실 / 공장` → `REL_WORK`.

**통근 관계어("퇴근길", "출근하다가")는 `COMMUTE`가 흡수한다.** 관계어를 셋으로 쪼개면 예산을 넘는다.

## 4. 스팬에 붙는 세 가지

### 4-1. `level` — 단서 등급

> **정의: `level`은 그 스팬이 *단독으로* 속성을 얼마나 확정하는가를 뜻한다.**
> 다른 스팬과의 조합 효과는 여기서 다루지 않는다 — 그건 C가 계산한다.

이 정의가 없으면 "집 근처"와 "신갈저수지"에 각각 무엇을 붙일지 답이 나오지 않는다.

| 등급 | 뜻 | 예 | 왜 |
|---|---|---|---|
| `explicit` | 값이 그대로 적힘 | 마흔여덟 | 단독으로 나이가 나온다 |
| `implicit` | 문맥상 거의 확정 | 완성차 공장 출장 | 단독으로 업종이 거의 확정된다 |
| `inferential` | 단독으로는 미확정 | 신갈저수지 / 집 근처 | 다른 스팬과 묶여야 좁혀진다 |

등급은 **스팬마다 하나** 부여하고, 전 스팬에 예외 없이 붙인다.

> ⚠️ **암묵-only ablation이 이 필드 위에서 재현된다.** 명시 단서 글을 제외해도 7속성이 유지되는지가 프로젝트 전제인데, `level` 정의가 흔들리면 *무엇을 제외한 실험인지*가 흔들린다.

### 4-2. `subject` — 누구의 정보인가

코퍼스 설계상 **오답 유도용 함정**을 심는다. "동탄 사는 친구랑 밤낚시"의 `동탄`은 본인 거주지가 아니다.

| 값 | 언제 |
|---|---|
| `self` | 기본. 문장이 타인 소유임을 밝히지 않았다 |
| `other` | 문장이 **명시적으로** 타인에게 귀속시켰다 — "친구가", "지인이", "옆집" |
| `unknown` | 문장만으로 판단 불가 |

**왜 필드를 하나 더 늘리면서까지 넣나 — 세 가지다.**

1. **함정 판별이 기존 도구와 갈리는 가시적 지점이다.** 지명이 나오면 무조건 거주지로 찍는 사전 기반 도구와 여기서 갈린다. `subject`가 없으면 *"동탄을 걸러냈다"*를 정량화할 방법이 없고, 「기존 도구 대비 추가 탐지율」의 질적 근거도 사라진다.
2. **제3자·미성년 정보 표시를 겸한다.** 셰어런팅 단서(자녀 정보)가 `other`로 잡힌다. 멘토 피드백에 미결로 올라 있는 항목이다.
3. **`risk`와 달리 일관 라벨이 된다.** `subject`는 **문장이 국소적으로** 말해준다(누구 것이라고 문장에 적혀 있나). `risk`는 글 전체를 봐야 한다. 그래서 하나는 라벨이 되고 하나는 안 된다.

> ⚠️ **`unknown`은 쓰레기통이 되기 쉽다.** *"문장만으로 판단 불가"*일 때만 쓰고, **W3 IAA에서 `subject` 일치도를 따로 측정한다.**

### 4-3. `type`

§3-2의 10개 중 하나. 부분 점수는 없다(§2-2).

## 5. 위치 표기와 경계

### 5-1. 좌표

| 항목 | 확정 |
|---|---|
| 단위 | **문자 offset** (토큰 인덱스·바이트 아님) |
| 구간 | `start` **포함** / `end` **미포함** — 파이썬 슬라이스와 동일 |
| 검증 | `text == body[start:end]` 가 항상 참이어야 한다 |

문자 offset을 쓰는 이유: **토크나이저는 바뀌지만 코퍼스는 살아남는다.**
`end` 포함/미포함을 안 정하면 **전 코퍼스가 한 글자씩 어긋난다.**

### 5-2. 경계 — 어절에 정렬한다

> **스팬은 단서를 이루는 명사구를 감싸되, 경계는 어절(공백)에 정렬한다.**
> **끝 어절의 조사·어미는 포함한다. 용언(서술어)은 제외한다.**

```
"첫째가 고등학교 배정 받았습니다"

✗ (4,11) "고등학교 배정"        ← 조사를 떼려다 스팬이 둘로 쪼개진다 = 최장 우선과 충돌
✗ (0,16) "첫째가 고등학교 배정 받았습니다"  ← 서술어까지 삼켰다
○ (0,11) "첫째가 고등학교 배정"
```

**조사를 떼는 판단이 IAA를 가장 많이 깎는 지점인데, 얻는 게 없다.** §2의 partial match와 짝을 이루면 조사 한두 글자는 F1에 영향을 주지 않는다. `text == body[start:end]` 검증도 어절 정렬이 훨씬 안전하다.

## 6. 겹침 규칙

> **겹침 금지 · 최장 우선.**

BIO 태깅은 토큰 하나에 라벨 하나만 붙일 수 있어 겹치는 스팬을 표현하지 못한다.
이건 취향이 아니라 **모델 구조에서 나오는 제약**이다. 계약이 겹침을 허용하면 코퍼스를 전부 다시 라벨해야 한다.

```
"집 근처라 자주 가는 신갈저수지"

✗ (0,17) 전체를 거주 단서로  +  (12,17) 신갈저수지를 시설로   ← 겹침, 표현 불가
○ (0,4)  집 근처   → REL_HOME       / inferential / self
  (12,17) 신갈저수지 → LOC_FACILITY  / inferential / self     ← 두 스팬으로 분리
```

관계어를 별도 유형으로 둔 이유가 이것이다. 붙여 잡으면 겹침이 생기고, 안 잡으면 "집 근처"가 사라진다.

## 7. BIO 밖에 두는 것 — 별도 레이어 2종

**스팬으로 잡지 않지만 버리지도 않는다.** 글 단위 플래그로 남긴다.

| 레이어 | 무엇 | 왜 BIO 밖인가 | 채점 |
|---|---|---|---|
| **밈·유행어** | 손민수 / 정병 / 에바 | 계획서 설계원칙 4 — *"밈은 모델이 아니라 사전. 파일 교체로 갱신, 재학습 불필요."* **태그셋에 넣으면 모델이 밈을 외우고 그 성질이 사라진다** | 사전 재현율·오탐률 (B 소유 `data/dict/signatures/meme.json`) |
| **세대 신호** | "무릎이 예전 같지 않네요" | 라벨러가 가장 많이 갈리는 표현이다. **B의 암묵 F1 목표치가 IAA에 묶여 있으므로, 갈리는 항목을 스팬에 넣으면 목표치가 같이 깎인다** | 글 단위 플래그 정확도 |

**세대 신호를 빼도 잃는 게 없다.** 계획서 §4가 1단의 일을 *"준식별자 스팬 탐지(BIO) · **문체/세대 신호** · 밈 사전 매칭"* 셋으로 이미 나눠뒀다. 스팬에서 빼도 2단은 그 문장을 그대로 보므로 나이 추론 근거로 계속 쓰인다 — 선행 PoC에서 이 표현이 근거로 잡힌 것도 2단 판정에서였다.

그리고 **경계를 정할 필요 자체가 사라진다** (*"무릎이"*부터인가 *"않네요"*까지인가).

## 8. 레코드 형식

### 8-1. 스팬

```json
{"start": 12, "end": 17, "text": "신갈저수지",
 "type": "LOC_FACILITY", "level": "inferential", "subject": "self"}
```

**스팬에 붙는 필드는 위 6개까지.** (B의 모델 출력에는 `score`가 추가된다 — 모델 확률값이며 위험도가 아니다.)

| 넣지 않는 필드 | 이유 |
|---|---|
| `risk` `severity` | 같은 표현의 위험도가 문맥마다 다르다. 일관 라벨이 불가능 → C가 계산 |
| `attr` | 유형-속성이 1:n이다. §3-2 매핑표로 대신한다 |

### 8-2. 글

```json
{"post_id": "S01_b07", "persona_id": "S01",
 "spans": [ ... ],
 "flags": {"gen_signal": true, "negative_control": false}}
```

### 8-3. `schema_version`

**jsonl 파일의 첫 줄에 헤더 레코드로 한 번 둔다.** 스팬마다 붙이지 않는다.

```json
{"schema_version": "1.0", "corpus_version": "v0", "created": "2026-08-24"}
```

계약 4종 전부에 `schema_version`이 들어가기로 되어 있고, 라벨 파일은 이 형태가 가장 싸다.

## 9. 유형 분포는 생성 단계에서 통제한다 (A)

§3-1의 "유형당 60~70 스팬"은 균등 분포일 때의 평균이다. 실제로는 `SEX`·`INCOME`·`REL_WORK`가 30개도 안 나올 수 있고, **그러면 그 유형의 F1이 무의미해지고 §3-1 예산표의 논거가 사후에 무너진다.**

**이 분포를 통제할 수 있는 사람은 A뿐이다** — 인물 JSON의 `clue_plan`이 어떤 유형이 몇 번 등장할지를 결정하기 때문이다. 코퍼스가 동결된 뒤에 세어보고 메우려면 늦는다.

> **인물 JSON 작성 규칙에 넣는다**: 인물 5명 묶음마다 `INCOME` · `SEX` · `REL_WORK` 단서를 **각 2건 이상** 배치한다.

W3 골드셋 검수 시 유형별 스팬 수를 세어 `experiments/`에 기록하고, 30개 미만인 유형은 **F1을 내지 않고 "표본 부족"으로 표기**한다.

## 10. 라벨하지 않는 것

**학력 · 학교 · 전공 · 정치성향 · 건강 · 지적 수준**은 유형 목록에 넣지 않는다.
방어 도구가 민감 속성 추론을 학습하면 그 자체가 무기가 된다.

**`type` enum에 이것들이 없다는 사실 자체가 RULES-DO-NOT #4의 강제 장치다.** 문서에 적어둔 규칙은 잊히지만 enum에 없는 값은 검사기가 잡는다.

## 11. 남은 미결 — 회의 안건

> v0.1의 미결 5건은 위에서 닫았다. 아래 4건이 새로 열린 것이고, **전부 B의 학습 파이프라인에 걸린다.**

| # | 안건 | 왜 지금 정해야 하나 |
|---|---|---|
| 1 | **W3 IAA 측정 대상** — `type`만인가, `level`·`subject`까지인가 | 셋 다 재면 일치도가 낮게 나오고, `type`만 재면 `subject` 품질을 모른다. **B의 암묵 F1 목표 산식이 여기서 나온다** |
| 2 | **네거티브 컨트롤 글의 검증 방법** | 라벨이 0개인 게 "제대로 매겼다"인지 "안 매겼다"인지 구분할 방법이 없다. 코퍼스의 10~15%가 여기 해당한다 |
| 3 | **`score` 임계값** (B 모델 출력) | 계약에는 필드만 두고 임계값은 실험으로 정할지, 기본값을 박을지 |
| 4 | **골드셋 파일 경로·분할** | `data/corpus/v0/gold/<이니셜>_spans.jsonl` 로 갈지, 인물 단위로 갈지 |

## 부록 — 샘플 문장 8개 (회의용)

**진행 방법**: 회의 시작 후 A·B가 **각자 따로 10분간** 라벨을 붙이고, **다른 부분만** 비교한다.
다른 부분이 곧 안건이다. W3 IAA 파일럿의 축소판이기도 하다.

```
S-1  집 근처라 자주 가는 신갈저수지 조황입니다. 요즘 사람이 부쩍 많네요.
S-2  동탄 사는 친구랑 밤낚시. 걔는 차로 20분이라 편하다고.
S-3  새벽에 나섰더니 무릎이 예전 같지 않네요. 마흔여덟이 이런 건가.
S-4  첫째가 고등학교 배정 받았습니다. 둘째는 아직 중학교.
S-5  퇴근하고 기흥호수 한 바퀴. 공장에서 15분이면 와서 자주 옵니다.
S-6  어제 본 드라마가 생각보다 재밌더라고요. 주말에 몰아볼 생각입니다.
S-7  요즘 부쩍 추워져서 아침마다 고민입니다. 그래도 겨울이 낫긴 하네요.
S-8  와이프가 장비값 얘기 또 꺼내서 이번 달은 조용히 넘어가려고요.
```

각 문장이 겨냥하는 결정:

| 문장 | 겨냥 |
|---|---|
| S-1 | 겹침 규칙(§6) · 관계어 분리(§3-3) |
| S-2 | **`subject` 함정 표시**(§4-2) |
| S-3 | **세대 신호를 BIO 밖으로**(§7) · `AGE`/`explicit` |
| S-4 | **스팬 경계**(§5-2) · 유형-속성 1:n |
| S-5 | 인접 유형 3종 혼재 · `REL_WORK` vs `COMMUTE` 귀속 |
| **S-6** | **네거티브 — 라벨 0개** (과탐 경계) |
| **S-7** | **네거티브 — 라벨 0개** (과탐 경계) |
| **S-8** | **희소 유형** `SEX` · `INCOME` |

> **네거티브 2문장을 넣은 이유**: 다섯 문장이 전부 단서를 담고 있으면 라벨러가 *"여기 뭔가 있다"*는 전제로 읽는다. **과탐 경계는 아무것도 라벨하지 않아야 하는 문장에서만 합의된다.**
> **S-8을 넣은 이유**: `SEX`·`INCOME`은 실제 코퍼스에서도 가장 희소할 유형인데, 샘플에 한 번도 안 나오면 규칙이 시험되지 않는다(§9).

# 계약 필드 대조표

> **네 계약이 같은 것을 같은 이름으로 부르는지 확인하는 문서.**
> 계약 본문이 아니다 — 각 필드의 정본은 소유 계약이다. 여기는 **가로로 비교**하는 자리다.

## 왜 있나

계약은 네 개인데 **받는 쪽은 겹친다.** 특히 E는 넷을 전부 받는다.

```
B span ──┐
C spec ──┼──→ D stage2 ──→ E 화면
C contr ─┘        └─────────→ E 화면
```

그래서 **한쪽에서 이름을 바꾸면 다른 쪽이 조용히 깨진다.** 타입이 맞으면 에러가 안 나기 때문에, 통합(W5)에 가서야 발견된다.

이 문서는 세 가지를 한다.

1. **필드마다 「무엇이고 어디에 쓰이나」** — 자기 계약 밖의 필드를 읽을 때
2. **§7 이름이 갈리는 자리** — 같은 것을 다르게 부르는 자리와 결정권자
3. **§8 값을 누가 채우는가** — 받는 모양은 정해졌는데 만들 사람이 안 정해진 자리

---

## 1. 무엇을 가리키는가 — 식별자

### `post_id`

글 하나의 식별자.

| | |
|---|---|
| 발급 | **가상 SNS(⑦, E)가 글을 만들 때 붙인다.** 나머지는 받아서 쓴다 |
| 쓰이는 곳 | C의 `delta`·`removed_post_ids` · D의 `evidence`·`targets` · E의 「이 글을 비공개하세요」에서 **어느 글인지** |

### `text_id`

**한 글 안의 어느 텍스트인가.**

| 값 | 단위 |
|---|---|
| `body` | 글 |
| `title` | 글 |
| `photo_caption:<n>` | 글 — **한 글에 여러 장.** 0부터, 표시 순서 |
| `profile_bio` | **사용자** |

**없으면 제목의 12번째 글자와 본문의 12번째 글자를 구분할 수 없다.** 단서가 본문에만 있지 않다는 게 리얼리즘 카드 실측에서 셋 나왔다 — S11 제목, S12 프로필 소개란(직업이 여기에만 있음), S13 사진 캡션.

| | |
|---|---|
| 정본 | `label-schema.md` §5-3 |
| 쓰이는 곳 | `start`/`end`의 **기준 텍스트** · C의 `top_spans` · E의 **형광펜을 어디에 칠지** |

> ⚠️ **`profile_bio`는 글이 아니라 사용자에 속한다.** 글마다 복제하면 같은 단서가 N번 세어져 C의 기여도가 망가진다. §3 `residual_risk` 참조.

> **이 목록은 가상 SNS가 실제로 제공하는 칸과 1:1이어야 한다.** 없는 칸을 계약에 두면 B가 없는 데서 스팬을 찾는다. 「가상 SNS 최소 스펙」(E)이 정본이다.

### `span_id`

**탐지된 단서 하나하나의 이름표.** 예 `S01_b07_s02`

| | |
|---|---|
| 형식 | `<post_id>_s<2자리>` · 프로필은 `<persona_id>_bio_s<2자리>` |
| 정본 | `label-schema.md` §8-1 |
| 쓰이는 곳 | D의 `Finding.evidence`(판정 근거) · C의 `top_spans`(기여 근거) · E의 **「왜요?」를 눌렀을 때 형광펜이 켜지는 연결** |

**왜 위치로는 안 되나 — 가명화하면 offset이 밀린다.**

```
원문    친구랑 신갈저수지 다녀왔다.
              └─ [4, 9)
가명화  친구랑 [경기의 특정 저수지] 다녀왔다.
              └─ [4, 15)
```

5글자가 11글자로 늘면서 **뒤의 모든 offset이 6씩 밀린다.** 위치로 가리키면 가명화 전후로 다른 곳을 가리킨다.

> **`span_id`가 없으면 화면에 이유를 못 쓴다.** 이유 없는 추천은 눌리지 않는다.

### `start` / `end`

`text_id`가 가리키는 텍스트 안의 문자 offset. **0-based, `end` 미포함** — 파이썬 슬라이스와 같다. 유니코드 코드포인트 기준, NFC.

검증식: `text == texts[text_id][start:end]` 가 항상 참.

## 2. 단서가 어떤 성질인가

> 정본 — `label-schema.md` (소유 A·B)

### `type`

준식별자 유형 **10종**(상한).

`AGE` `SEX` `LOC_ADMIN` `LOC_FACILITY` `REL_HOME` `REL_WORK` `JOB` `FAM` `COMMUTE` `INCOME`

밈·유행어와 세대 신호는 **여기 없다** — BIO 밖 별도 레이어로 글 단위 플래그다.

### `level`

**이 단서 하나가 단독으로** 얼마나 확정적인가.

| 값 | |
|---|---|
| `explicit` | 대놓고 적음 |
| `implicit` | 간접적 |
| `inferential` | 추론이 필요함 |

조합 효과는 여기 없다 — 그건 C가 계산한다.

> ⚠️ **C의 `specificity`에도 `level`이 있는데 뜻이 다르다.** §7-② 참조.

### `subject`

**이게 누구 정보인가.** `self` / `other` / `unknown`

**문장이 국소적으로 말해주는 것만 본다** — 앞뒤 문장을 읽어야 갈리는 사례는 만들지 않는다(라벨러마다 어디까지 읽었는지가 달라져 IAA가 깎인다).

쓰이는 곳 — D는 `other` 스팬을 `evidence`에 넣지 않는다. E는 셰어런팅 경고를 띄운다.

## 3. 위험을 얼마로 재는가

> 정본 — `specificity.schema.json` · `contribution.schema.json` (소유 C)

### `k`

**이 조건에 해당하는 사람이 몇 명 남는가.** 적을수록 위험.

> ⚠️ **못 구하면 `null`이다. `0`이 아니다.** `0`은 「해당자 없음」이라 위험도 최대로 읽힌다. 화면에서도 `null`을 「0명」으로 표시하면 안 된다.

정확히는 **k-익명성 근사**다. 문서·발표에서 「k-익명성을 적용했다」로 쓰지 않는다.

### `k_level`

k를 등급으로. `VERY_HIGH` / `HIGH` / `ACCEPTABLE` / `UNKNOWN`

**경계값은 `plan.md` §13.1이 소유한다** — `k≤2` 매우높음 / `3~4` 높음 / `≥5` 통상허용. 근거가 데이터가 아니라 **개인정보위 가명정보 처리 가이드라인**이고, W1에 선언한 성공 기준(「위험도의 법적 정박」)이다.

> **한글 문구는 E가 매핑한다.** 코드 값은 영문 상수다 — 문구를 다듬을 때마다 남의 코드가 깨지면 안 된다.

### `basis`

그 k가 **어느 통계 · 몇 년 몇 월 기준**인가. `{source, as_of}`

**심사에서 반드시 묻는다.** 「이 숫자 어디서 나왔나」에 답할 수 있는 유일한 필드다. 화면에는 숫자 옆 작은 글씨로 붙는다.

### `risk` / `baseline_risk`

**0~100 실수, 높을수록 위험.** k와는 다른 출력이다 — k는 법적 등급, 0~100은 서비스 표시 점수.

### `delta`

**이 글 하나를 비공개했을 때의 위험도 변화. 내려가면 음수.** 예 `-18.0`

> ⚠️ **부호가 이 필드의 전부다.** `-18`이 「18 내려간다」인지 「18 올라간다」인지 어긋나면 **에러 없이 반대로 추천한다.**

쓰이는 곳 — E의 정렬 키. `|delta|` 내림차순으로 「이 글부터 처리하세요」.

### `greedy_path`

하나 빼고 → 다시 계산 → 다음을 빼는 **경로**.

> ⚠️ **`delta` 상위 3개를 더하면 안 된다.** 단서가 두 글에 겹치면 기대보다 크게 떨어지고, 둘이 있어야 좁혀지는 관계면 작게 떨어진다. 화면의 「3개 빼면 79.7 → 41」은 **`greedy_path`의 마지막 값**이지 합이 아니다. **합으로 띄우면 조용히 틀린 숫자가 나간다.**

### `residual_risk` · `user_scoped`

**글을 전부 비공개해도 남는 위험도**와, 그 몫을 만드는 **글에 속하지 않는 단서** 목록.

프로필 소개란·닉네임·게시 패턴은 `removed_post_ids`로 사라지지 않는다. 이걸 모델링하지 않고 프로필 스팬을 글마다 복제하면, **글을 전부 지웠을 때 `risk_after`가 0으로 떨어진다** — 프로필은 그대로 공개돼 있는데도.

```
recompute.risk_after  ≥  residual_risk        (항상)
```

**이 식 하나가 그 버그를 자동으로 잡는다.**

## 4. 무엇으로 판정하고 무엇을 권하는가

> 정본 — `stage2-io.schema.json` (소유 D)

### `verdict`

**7속성 각각**의 판정. `specified` / `narrowed` / `weak_signal` / `abstain`

**실제 값은 산출하지 않는다** — 「무엇이 특정 가능한가」까지다. 화면 문구는 E가 매핑한다.

> **`abstain`이 `required`인 이유** — 「근거가 없으면 기권한다」가 원칙인데, 필드가 없으면 **기권을 표현할 방법 자체가 없다.**

### `granularity`

어디까지 좁혀졌나. `sido` / `sigungu` / `eupmyeondong` / `facility_radius` / `decade` / `half_decade` / `exact_year` / `category` / `null`

### `evidence`

판정 근거. `post_id` + `span_id` 쌍.

> ⚠️ **실제 지명·이름이 들어가지 않는다.** 가명 라벨과 id만 담는다 — 원문을 넣으면 **방어 도구가 아니라 추론기가 된다.**

### `action_type` · `burden` · `targets` · `projected_delta`

조치 추천 한 건. `unpublish` / `activity_meta` / `rewrite`

- **`burden`이 정렬 키다** — 부담 낮은 것부터
- `targets.kind` — `post` / `meta_field`(닉네임·위치태그·게시시각) / **`profile`**(프로필 소개란)
- 삭제 권고는 `actions`가 아니라 `exceptional`로 **분리한다**

### `schema_version` · `provenance`

어느 계약 버전으로, 어느 모델·사전·데이터로, 언제 계산했는가. **모든 수치에 측정일·데이터 버전·모델 버전이 붙는다.**

## 5. 사슬 하나 — 필드가 어떻게 이어지는가

프로필에만 직업이 있는 인물(S12 실측)에서 화면 문구가 나오기까지.

```
B  span    {span_id:"S01_bio_s01", text_id:"profile_bio", type:"JOB"}
             ↓
C  contr   user_scoped[{source:"profile_bio", delta:-34,
                        top_spans:[{span_id:"S01_bio_s01", …}]}]
           residual_risk: 34
             ↓
D  stage2  findings.occupation {verdict:"specified",
                                evidence:[{span_id:"S01_bio_s01"}]}
           Action{rewrite, targets:[{kind:"profile", ref:"profile_bio"}],
                  projected_delta:-34}
             ↓
E  화면    "프로필 소개란을 고치면 34 내려갑니다"  + 그 문장에 형광펜
```

**중간 어느 한 칸에서 이름이 갈리면 사슬이 끊긴다.** 그런데 타입은 다 맞으므로 에러가 안 난다.

## 6. 표기 규약

| 항목 | 규약 |
|---|---|
| 코드 값 | **영문 상수.** 한글은 화면 문구이며 E가 매핑한다 |
| 「못 구했다」 | **`null`.** `0`을 쓰지 않는다 |
| offset | 문자, 0-based, `end` 미포함, NFC |
| 행정구역 키 | **행정표준코드 문자열** — 정수로 두면 앞자리 0이 죽는다 |
| 버전 | 계약 4종 전부에 `schema_version` |

## 7. 이름이 갈리는 자리

⚠️ **이 절은 초안을 비교하던 시점에 쓰였다.** 그 뒤로 계약이 머지되면서 셋 중 둘이 정리됐다.
아래는 **2026-08-27 기준 계약 실물을 확인한 결과**다. 표만 보고 「아직 안 정해졌다」고 읽지 않도록 상태를 앞에 둔다.

| | 무엇 | 상태 |
|---|---|---|
| ① | 사용자를 부르는 이름 | ✅ **정리됨** — 머지된 계약 넷이 전부 `user_ref` |
| ② | `level`이 두 뜻 | ✅ **정리됨** — C는 `k_level`로, D는 [#62](../../../../pull/62)로 맞춤 |
| ③ | `age_band` 단위 | ⏳ **방향만 정해짐** — 정규식이 아직 `40-49`를 통과시킨다 |

### ① 사용자를 부르는 이름 — ✅ 정리됨

초안 시점에는 넷이었다.

| 문서 | 표기 | |
|---|---|---|
| A `label-schema` | `persona_id` | 합성 코퍼스 인물 — **별개가 맞다** |
| C 초안 `C-specificity.md` §9 | `user_id` | 같은 것 |
| C 초안 `howto/e-contracts.md` §3-3 | `author_id` | 같은 것 |
| D `stage2-io` | `user_ref` | 같은 것 |

**`user_ref`로 정리됐다.** 형식이 박혀 있는 유일한 이름이라(`^u_[0-9a-f]{8,}$`) 실제 닉네임을 넣으면 튕긴다. 나머지 둘은 맨 문자열이라 그냥 통과했다.

머지된 계약 실물을 확인한 결과다.

```
span.schema.json          (해당 필드 없음)
stage2-io.schema.json     user_ref
specificity.schema.json   user_ref
contribution.schema.json  user_ref
```

`user_id`·`author_id`는 **계약에 한 곳도 안 남아 있다.** C 초안 문서에만 있던 이름이다.
`persona_id`는 `label-schema`에 남아 있는데, 그건 **합성 코퍼스 인물 식별자**라 런타임 사용자와 별개가 맞다 — `span_id` 규약(`<persona_id>_bio_s<2자리>`)에서 쓴다.

### ② `level`이 두 뜻으로 쓰인다 — ✅ 정리됨

| 계약 | 뜻 | 값 |
|---|---|---|
| A `label-schema` (+ D `Span.level`) | **단서 등급** | `explicit` `implicit` `inferential` |
| C `specificity` | **위험 등급** | `VERY_HIGH` `HIGH` `ACCEPTABLE` `UNKNOWN` |

`C-specificity.md` §9가 같은 원칙을 이미 적어뒀다 — *「한 이름에 뜻이 셋이면 반드시 어긋난다」*(그래서 조건 해상도를 `resolution`으로 뺐다).

**C가 `k_level`로 바꿔서 C 쪽은 정리됐다.**

⚠️ **그런데 D 쪽이 안 따라가 있었다.** 이 표는 「A vs C」로 적혀 있었지만, 실제로 남아 있던 어긋남은 **`stage2-io` 안**이었다.

```
Span.level                       explicit · implicit · inferential      ← 단서 등급
InputPost.specificity.level      SAFE · ACCEPTABLE · RISKY · CRITICAL   ← 위험 등급
```

한 계약 안에서 한 이름이 두 뜻이었고, 값도 C와 달랐다. **C 출력을 D 입력에 그대로 넣으면 실패했다.**

```
C 출력 -> D 의 specificity 칸 : 실패
   'level' is a required property
```

[#62](../../../../pull/62)에서 셋을 맞췄다 — 이름 `level`→`k_level`, 값 `SAFE` 계열→`VERY_HIGH` 계열, 타입 `integer`→`number`.
마지막 것이 조용한 함정이었다. C의 `k`는 **추정값**이라 감쇠 계수를 곱하면 정수로 안 떨어지는데, `integer`로 조여 놔서 `k=3.5`가 튕겼다.

### ③ `age_band` 단위 — ⏳ 방향만 정해짐

초안은 10년(`"40s"`)인데 **주민등록 인구통계 교차표는 5년**(`"40-44"`)이다.

**5년으로 정해졌다.** 5년은 10년으로 합칠 수 있지만 반대는 불가능하다.

⚠️ **아직 스키마에 반영이 안 됐다.** `specificity.schema.json`의 정규식이 이렇다.

```
^([0-9]{1,3}-[0-9]{1,3}|[0-9]{1,3}\+)$
```

`40-49`(10년 구간)가 통과한다. 바로 위 `$comment`는 「교차표가 5년 단위라 «40대» 같은 값이 들어오면 조회가 안 된다」고 써 놨는데, **주석과 검증이 어긋나 있다.**

그리고 개방 구간이 `90+`와 `100+` **둘 다** 통과한다. 둘 다 허용하면 같은 92세가 두 값으로 조회돼 **k가 갈린다.** 5세 단위 강제보다 이쪽이 실제로는 더 중요하다.

## 8. 값을 누가 채우는가 — 생산자가 없는 필드

§7 이 「같은 것을 다른 이름으로 부르는 자리」였다면, 여기는 **이름은 하나인데 그 값을 만들 사람이 정해지지 않은 자리**다.

`stage2-io.schema.json` 의 `InputPost` 는 2단이 **받는** 모양을 정한다. 받는 모양이 정해져 있다고 해서 그걸 만드는 쪽이 정해진 것은 아니다. 계약 6종을 훑어 보면 **네 필드가 `stage2-io` 에만 있다.**

| 필드 | 정의된 곳 | 필수 | 생산자 | 상태 |
|---|---|---|---|---|
| `pseudonym_map` | `stage2-io` 만 | **필수** | 가명화기 (C·D) | ✅ **합의됨** — 절만 쓰면 된다 |
| `doc_flags.dialect_hits` | `stage2-io` 만 | 선택 | ? | 🔴 B 의 `flags` 에 없어서 아무도 안 낸다 |
| `activity_meta` | `stage2-io` 만 | 선택 | ? | 🟡 활동 메타 조치의 입력인데 출처 미정 |
| `triage_reason` | `stage2-io` 만 | 선택 | 트리아지 (D?) | 🟡 누가 트리아지하는지 미정 |

나머지는 생산자가 있다. `post_id` · `spans` · `texts` 는 B(`span.schema.json`)와 `label-schema.md` 에 있고, `specificity` · `contribution` 은 C 의 두 계약이 낸다.

### ① `pseudonym_map` — ✅ 합의됨, 절만 쓰면 된다

`InputPost.required` 에 들어 있다. **없으면 2단 입력이 스키마 검증에서 떨어진다.**

가명화기는 `geo-dictionary.md` 가 C·D 공동 소유로 잡고 있지만, 그 문서는 **지명을 무엇으로 바꿀지**를 정하지 지명·가명 쌍을 **어떤 모양으로 넘길지**는 정하지 않는다. 지금은 `stage2-io` 의 `PseudonymEntry` 가 유일한 정의이고, 그건 「내가 받는 모양」이지 「네가 내는 모양」이 아니다.

**`geo-dictionary.md` 에 출력 절을 두고 `PseudonymEntry` 를 정본으로 참조한다.** 새 스키마 파일을 만들 만큼 큰 구조가 아니고, 가명화기 소유자가 그 문서를 이미 보고 있다.

> ✅ 합의 — **C** (2026-08-27, [#39](../../../../pull/39) 코멘트)
> 필드 6개 · offset 기준 §4 그대로 · 절은 **D** 가 쓴다
>
> ⏳ 함께 확정할 것 — `restore_key` 의 `candidates`.
> `ambiguous: true` 일 때 `code: null` 만 주면 **지역 축이 통째로 빠져 모집단이 전국이 된다.**
> 그러면 k 가 실제보다 크게 나오고 위험도가 낮게 나온다.
> `geo-dictionary.md` §8 체크리스트에도 같은 항목이 있다.

### ② `dialect_hits` — 생산자가 없다 🔴

`DocFlags` 는 셋을 받는데 B 는 둘만 낸다.

```
B 가 내는 flags (span.schema.json) : gen_signal · meme_hits
D 가 받는 flags (stage2-io)        : gen_signal · meme_hits · dialect_hits
```

`required` 가 아니라 스키마 검증은 통과한다. **그래서 조용히 비어 있게 된다.** 값이 안 오는 것과 값이 없다고 판정한 것을 구분할 수 없다.

여태 안 걸린 이유는 코퍼스에 방언 표본이 없어서다. #55 의 D05(전남 담양 · 68F)를 넣으면서 생산자가 필요해졌다 — S15 카드의 대표 발견이 **「지명을 한 번도 안 쓰는데 방언이 지역군을 좁힌다」** 이고, 그 서술이 이미 `stage2-io` 의 `dialect_hits` 설명에 근거로 들어가 있다.

세 갈래가 있다.

| | 어떻게 | 걸리는 것 |
|---|---|---|
| **B 가 낸다** | `span.schema.json` 의 `flags` 에 추가 | 사전 매칭은 KoELECTRA 가 하는 일이 아니다 |
| **A 의 사전 레이어가 낸다** | `dialect.json` 이 A 소유라 자연스럽다 | B 출력과 사전 출력을 **어디서 합치는지** 정해야 한다 |
| **D 가 2단에서 직접 맞춘다** | 내 내부 값이 된다 | ❌ **안 된다.** C 의 k 계산이 `{axis: location, kind: dialect_region}` 으로 이걸 쓴다 — 내 내부 값이면 C 가 못 쓴다 |

세 번째는 빠진다. `meme_hits` 도 같은 성격(사전 레이어)이면서 B 의 `flags` 에 있으니, **`meme_hits` 를 누가 채우고 있는지가 곧 답이다.**

> 결정 — **A · B**

### ③ `Span.additionalProperties: true` 가 받치고 있다

기록해 둔다. B 가 내는 스팬에는 `text` 와 `score` 가 있는데 **`stage2-io` 의 `Span` 에는 둘 다 없다.**

```
B 만 내는 키 : score · text
D 만 받는 키 : (없음)
```

지금 통과하는 이유는 `Span.additionalProperties` 가 `true` 이기 때문이다. 의도한 것이다 — 2단은 `text` 를 쓰고 `score` 는 안 쓰지만, 안 쓴다고 거를 이유가 없다.

**나중에 이걸 `false` 로 조이면 B → D 연결이 끊긴다.** 조일 일이 있으면 `text` 와 `score` 를 명시적으로 넣고 조여야 한다.

>

>
> ⚠️ **DEC-002·003은 이 기준 이전에 쓰인 것**이라 저장소 운영 규칙인데도 남아 있다. 과거 기록으로 두고 새로 만들지 않는다. 해당 규칙의 정본은 [`.gitignore`](../.gitignore)와 [`submissions/README.md`](../submissions/README.md)다.

> **운영 규칙**
> - **append-only.** 결정을 뒤집을 때는 기존 항목을 지우지 말고 상태를 `Superseded by DEC-NNN`으로 바꾸고 새 항목을 추가한다.

## [DEC-003] 마일스톤 원고도 드라이브로 — 새 내용은 `docs/`에 둔다

**상태**: Accepted · W2 (2026-08-24)
**대체 대상**: [DEC-002](#dec-002-저장소는-제출본이-아니라-원고를-담는다)의 *"마일스톤 산출물의 원고(`*_내용.md`)는 저장소에 남긴다"* 조항. **그 조항만** 대체하며 나머지는 유효하다.

### 맥락

DEC-002는 마일스톤 원고를 저장소에 남기기로 했다. 근거는 *"개정되고 나중에 비교된다 — 8주차 「계획 대비 변경사항」·10주차 「중간 점검 이후 개선사항」의 원자료가 이 diff다"* 였다.

W2 수행계획서를 실제로 써 보니 **그 근거가 성립하지 않는다.**

1. **개정되지 않는다.** 수행계획서는 금요일에 제출하면 다시 고치지 않는다. W4 설계서는 다른 문서고 W8 중간점검도 다른 문서다. **diff할 대상이 생기지 않는다.**
2. **대부분이 `docs/`의 파생물이다.** 주차별 계획은 [roadmap.md §2](roadmap.md), 역할·담당기간은 [plan.md §9](plan.md), 데이터 계획은 [plan.md §6](plan.md), 기술·환경은 [plan.md §4·§9](plan.md)에서 그대로 나온다. **diff 가능한 정본은 이미 저장소에 있고 그쪽이 개정된다.** 제출용 렌더링을 함께 커밋하면 중복이고, 중복은 어긋난다.

### 결정

**마일스톤 산출물의 원고도 팀 드라이브로 보낸다.** 저장소에 남는 것은 증빙(`evidence/`)과 제출 이력뿐이다.

**단, 원고에만 있고 `docs/`에 없는 내용은 먼저 `docs/`로 옮긴다.** 그러지 않으면 원고와 함께 사라진다.

| 옮긴 내용 | 옮긴 곳 |
|---|---|
| 진행률 산정 규칙 (컴포넌트 가중치·운용 3규칙) | **[roadmap.md §9](roadmap.md)** (신설) |
| API 토큰 예산 배분 (M1 50 / M2 20 / M3 15 / M4 15) | [plan.md §9](plan.md) |
| D 부하 재배치 조항 | [plan.md §9](plan.md) |
| 협회 실습 데이터셋 미신청 + 사유 | [plan.md §6](plan.md) |
| RTX 3060 VRAM 12GB → **8GB 실측 정정** | [plan.md §9](plan.md) |

### 근거 — 진행률 규칙이 특히 중요하다

이 규칙은 **hwp 양식에 칸이 아예 없어서** 원고에만 존재했다. 그대로 드라이브로 보내면, W8에 근거가 필요한 규칙이 정확히 DEC-002가 우려한 *"카톡·드라이브로 흩어진다"* 의 사례가 된다. `roadmap.md`가 주차·게이트·판정을 소유하므로 거기가 제 자리다.

### 결과

**규칙이 하나로 정리된다** — `docs/`가 정본, 제출 원고는 렌더링. W4 설계서·W8 중간점검·W10 결과정리서에도 같은 방식이 적용된다. 새 내용이 생기면 원고가 아니라 `docs/`에 먼저 쓴다.

**잃는 것과 대응** — 제출 원고의 문장 그대로를 저장소에서 인용할 수 없게 된다. 다만 원고는 `docs/`의 파생물이므로 인용해야 할 내용은 `docs/`에 있다.

**이행**

1. `.gitignore`에 `/submissions/milestones/**/*.md` 추가
2. `submissions/README.md` 보관 위치 표 갱신
3. 이미 추적 중인 `submissions/milestones/W01-주제선정서/주제선정서_내용.md`는 **별건으로 추적 해제** — 드라이브 업로드 확인 후
4. 히스토리는 손대지 않는다

## [DEC-002] 저장소는 제출본이 아니라 원고를 담는다

**상태**: Accepted · W2 (2026-08-24)
**대체 대상**: `submissions/README.md` 「여기만 hwp·pptx 가 버전관리된다」, `.gitignore` 의 `!/submissions/**/*.hwp` 예외

### 맥락

기존 규칙은 `*.hwp` 를 전면 제외한 뒤 `submissions/` 만 예외로 되살렸다. 근거는 *"그렇게 하지 않으면 주간보고 12편 + 산출물 6종이 통째로 빠져 버전관리가 카톡·드라이브로 흩어진다"* 였다.

W2 검토에서 이 근거가 **대상별로 성립하지 않는다**는 점이 확인됐다.

1. **주간활동보고서는 팀원이 저장소에서 볼 필요가 없다.** 서명은 PM이 작성본을 카카오톡·디스코드에 올리고 팀원이 확인 후 서명해 돌려주는 방식으로 이미 운영 중이다.
2. **주간보고는 매주 새 문서이지 개정본이 아니다.** W02 와 W03 을 diff 해도 얻을 것이 없다. 버전관리의 핵심 이득이 이 문서군에는 적용되지 않는다.
3. **증빙 논거가 성립하지 않는다.** `scripts/weekly_report.sh` 는 git log 를 읽어 증빙을 *생산*할 뿐이고 출력은 `docs/evidence/` 로 간다. 보고서가 저장소에 있어야 하는 구조가 아니다. 제출 분쟁의 근거도 `submissions/README.md` 가 이미 *"제출 완료 화면 캡처"* 로 정해 두었다.
4. **hwp 는 diff 가 되지 않는다.** 버전관리로 얻는 것이 백업·타임스탬프뿐인데 그건 팀 드라이브도 준다. 반면 실명이 실리는 최고위험 파일 종류이며, 이를 되살리기 위해 `.gitignore` 에 예외를 두는 바람에 서명본 차단 규칙이 그 예외 **뒤에** 와야만 효력이 있는 취약한 순서 의존이 생겼다.

### 결정

**저장소에 남기는 것**

- 마일스톤 산출물의 **원고**(`*_내용.md`)
- 증빙 캡처(`evidence/`)
- 제출 이력(`submissions/README.md` 표)

**팀 드라이브로 보내는 것**

- 제출본 전부(`*.hwp` `*.hwpx` `*.pptx`) — 마일스톤 포함
- 주간활동보고서 — **원고까지 포함**
- 서명·날인본, 자필 서명 이미지 (기존과 동일)

`.gitignore` 의 `!/submissions/**/*.hwp|hwpx|pptx` 예외 3줄을 삭제하고, `/submissions/weekly/**/*.md` 를 추가한다.

### 근거 — 마일스톤 원고만 남기는 이유

주간보고와 달리 마일스톤 산출물은 **개정되고 나중에 비교된다.**

- 8주차 중간점검보고서 양식에 「**계획 대비 변경사항 – 최초 설계에서 변경된 내용과 변경 이유**」 칸이 있다(양식 원본 확인).
- 10주차에 「중간 점검 이후 개선사항」이 이어진다.
- 2주차 수행계획서의 12행 그리드가 **8주차 진행률과 10주차 달성도의 분모**다.

셋 다 원문이 변형 없이 남아 있어야 산출된다. 이메일로 나간 hwp 만 있으면 6주 뒤에 기억으로 복원해야 한다. 그래서 **원고는 남기고 제출본은 보낸다.**

### 결과

**얻는 것**

- 실명·서명이 실리는 파일 종류가 저장소에서 사라진다. 서명본 차단이 `.gitignore` 규칙 **순서**에 의존하던 취약점도 함께 해소된다.
- 바이너리가 빠져 저장소가 가벼워지고, PR diff 가 읽히는 변경만 남는다.

**잃는 것과 대응**

- 제출본의 타임스탬프 백업 → 팀 드라이브 + 제출 완료 화면 캡처(`evidence/`)로 대체. 이미 그것이 유일한 분쟁 근거로 정해져 있다.
- 주간보고 12편을 한자리에서 훑는 편의 → 드라이브 폴더로 동일하게 확보.

**이행 순서**

1. 규칙 변경(이 PR) — `.gitignore` · `submissions/README.md` · 본 기록
2. **이미 추적 중인 W1 파일의 추적 해제는 별건으로 처리한다.** `.gitignore` 는 추적 중인 파일에 영향을 주지 않으며, 현재 열린 PR #1 이 같은 W1 hwp 를 수정하고 있어 동시에 지우면 충돌한다. PR #1 머지 후 `git rm --cached` 로 정리한다.
3. 히스토리에 남은 W1 hwp 는 그대로 둔다 — **서명 전 원본**이므로 제거 사유가 없다.

**↳ 갱신 2026-08-24 — 마일스톤 원고 조항이 대체됨**

이 항목의 *"마일스톤 산출물의 원고(`*_내용.md`)는 저장소에 남긴다"* 조항은 **[DEC-003]으로 대체되었다.** 근거였던 「개정되고 나중에 비교된다」가 W2 수행계획서를 실제로 써 보니 성립하지 않았다 — 제출 후 개정되지 않고, 내용 대부분이 `docs/`의 파생물이다.

**나머지 조항은 그대로 유효하다** — 제출본(hwp·pptx)과 주간활동보고서를 드라이브로 보내는 것, 증빙·제출 이력을 저장소에 남기는 것, 서명본 차단.

## [DEC-001] 입력·수집 경로를 자체 가상 SNS 플랫폼으로 한다

**상태**: Accepted · W1 · 관련 [MF-001](mentor-log.md)
**대체 대상**: 계획서 v2.1 §4 「입력 — 수집 경로는 브라우저 확장이다」, §5 컴포넌트 ⑦, §6 「데모용 블로그」

### 맥락

계획서 v2.1은 입력 경로를 **브라우저 확장**으로 정했다. 근거는 두 가지였다. ① 네이버가 본인 블로그 글 조회 API를 제공하지 않으므로(네아로=프로필만, 블로그 검색=전체 공개 대상, 글쓰기 API 2020.5 종료) 크롤링 외에 프로그램 경로가 없고, 크롤링은 상용 서비스로 약관 회색지대다. ② 확장은 사용자가 열람 중인 자기 페이지를 읽는 것이라 데이터가 브라우저를 벗어나지 않아 §2 자기모순이 해소된다.

W1 멘토링에서 두 가지 문제가 제기됐다.

1. 확장을 특정 블로그 플랫폼 에디터에 적용할 때, **현재 작성 중인 글 외에 기존에 작성해둔 게시글에 접근할 수 있을지 기술적으로 불확실**하다.
2. 결과물이 **특정 플랫폼 전용 도구로 한정되어 보일 수 있다.**

### 결정

**입력 경로를 자체 가상 SNS 플랫폼(웹 서비스)으로 변경한다.** 시스템 입력은 플랫폼이 아니라 스키마로 정의하고, 가상 SNS를 그 스키마를 충족하는 입력 어댑터의 하나로 둔다.

```
{ post_id, body, created_at, activity_meta{ nickname, geo_tag, post_time } }
```

어댑터는 3종: **가상 SNS**(개발·시연 주 경로) / **수동 업로드**(최소 기능, M4 검증용) / 플랫폼별 수집 확장(범위 밖).

### 근거

**결정적인 것은 두 번째 문제가 아니라 첫 번째다.** 수집 범위가 '작성 중인 글'로 한정되면 이 프로젝트의 핵심 주장을 시연·검증할 수단 자체가 사라진다.

- H3 누적 곡선 — 글 1편 위험도 26.7 → 5편 69.2 → 19편 79.7 *(선행 PoC 자체 측정)*
- ③누적·기여도 엔진 — 글 단위 한계 기여도("이 글을 비공개하면 −18")
- 최소 조치 추천 — "이 3개를 비공개하면 79.7 → 41"

셋 다 **글 이력 전체에 대한 접근을 전제**한다. 계획서 §6도 *"③누적 컴포넌트는 '같은 사람의 글 여러 편'이라는 구조 없이는 학습도 평가도 불가능하다"*고 명시했다.

즉 수집 경로 제약은 편의성 문제가 아니라 **핵심 컴포넌트의 검증 표면**에 관한 문제다.

### 결과

**얻는 것**

| | |
|---|---|
| 핵심 주장 시연 가능 | 누적 곡선·기여도·최소 조치 추천 전부 |
| 플랫폼 종속성 제거 | 입력 스키마 + 어댑터 구조로 일반성 확보 |
| 착수 시점이 당겨짐 | 외부 의존이 없어 M1(W3)부터 가능 → **E의 M3~M4 폭증 완화** |
| GT 완전 통제 | 합성 코퍼스 구조 = 데모 환경 구조 |
| 소멸한 작업 | 실계정 20편 수동 게시(1인 하루), 발행일 소급 대응, 발표 후 비공개 전환, 데모 계정 명의자 지정 |
| 복귀한 기능 | **에디터 실시간 경고** — 자체 에디터라 난이도가 내려갔다. **작성 시각 단서** — 소급 제약이 없어 시연 가능 |
| 발표 리스크 감소 | 외부 서비스의 로그인·네트워크·UI 변경에 의존하지 않음 |

**잃는 것 / 대응**

| 잃는 것 | 대응 |
|---|---|
| *"실제 서비스 환경 그대로"* 주장 | **하지 않는다.** 그 자리는 수동 업로드 경로 + M4 동의 실블로거 검증이 맡는다 |
| 자기모순 해소 논거의 기존 형태 | **플랫폼 계층 ↔ 분석 계층 분리**로 재구성 (아래) |

### ⚠️ 필수 후속 조치 — 자기모순 논거 재설계

v2.1 README·계획서는 *"크롤링 웹서비스 = 데이터 위치 우리 서버 = §2 자기모순 **위반**"*이라고 **우리 손으로 서술했다.** 이 서술을 그대로 두고 웹 서비스로 가면 논리가 정면 충돌한다.

**재구성**: 가상 SNS는 *우리가 제공하는 서비스*가 아니라 *사용자 데이터가 존재하는 플랫폼 자리를 대신하는 실험 환경*이다. 분석 도구는 여전히 사용자 측에서 실행되며 외부 전송은 0이다.

```
[SNS 플랫폼 계층]  ← 실서비스에서는 네이버·인스타가 오는 자리
      │ 입력 어댑터
[분석 계층]        ← 우리 제품. 사용자 측 실행. 외부 전송 0
```

**두 계층을 한 서버에 합치면 이 논거가 깨진다.** W2 모듈 인터페이스 계약에 계층 경계를 명시하고, 발표 데모에서 **브라우저 네트워크 탭으로 외부 요청 0건을 실증**한다.

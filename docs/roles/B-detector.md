## 0. 이 역할이 없으면 무슨 일이 생기나

**"외부 전송 0"이라는 주장이 무너진다.**

이 프로젝트의 논리는 이렇다 — 프라이버시 위험을 검사한다고 사용자 글을 외부 AI에 보내면 그 도구 자체가 침해다. 그래서 탐지는 사용자 컴퓨터 안에서 돌아야 하고, 그러려면 **작고 빠른 모델**이 필요하다. 그게 이 자리에서 만드는 모델이다.

그리고 하나 더 — **이 자리가 프로젝트의 존재 이유를 숫자로 증명한다.** 기존 개인정보 탐지 도구가 놓치는 걸 우리가 얼마나 잡는지, 그 격차를 재는 게 여기다. 격차가 없으면 *"이미 있는 것 아닌가"* 에 답할 말이 없다.

## 1. 무엇을 만드나

글을 넣으면 **신상 단서가 있는 구간에 밑줄을 긋고 종류를 붙여주는 모델**이다.

```
입력:  "집 근처라 자주 가는 신갈저수지 조황입니다. 마흔여덟 되니…"

출력:  신갈저수지 → [지역·시설]
       마흔여덟   → [나이]
       집 근처    → [거주 관계어]
```

| 산출물 | 규모·형태 | 언제 |
|---|---|---|
| 기존 도구 3종 실행 환경 + **미탐 목록** | 도구 3종이 같은 입력에 돌아감 · 미탐 스팬 목록 1건 | **W2** |
| 스팬 출력 계약 `span.schema.json` | JSON Schema 1건 (E에게) | **W2** |
| **베이스라인 3종 측정 결과** ⭐ | `metrics.json` — 등급별 분해 포함 | **W3** |
| 학습 파이프라인 (데이터 로더 · 학습 · 평가) | 스크립트 3종 + 재개 가능한 체크포인트 | W4 |
| **1단 탐지 모델 v1** | 체크포인트 + `models/registry.md` 1행 | W5~W7 |
| **밈·유행어 시그니처 사전** (§4.1) | `data/dict/signatures/meme.json` — 모델과 별도로 갱신 | W5~W7 |
| 성능 리포트 | 스팬 F1(등급별) · 재현율 · CPU 지연 | W7 |
| 벤치마크 러너 | 전체 성능을 한 번에 재는 스크립트 | W9~W10 |

**모델 가중치는 repo에 커밋하지 않는다.** `.gitignore`가 막는다. [`models/registry.md`](../../models/registry.md)에 포인터와 학습일·데이터 버전·지표만 적는다. 1단 탐지기는 **방어 측**이라 M4에 공개 대상이고, 그래서 학습에 쓰는 데이터의 라이선스가 중요하다(§12).

## 2. 먼저 알아야 할 개념 넷

파인튜닝을 처음 한다면 여기가 제일 중요하다. 용어를 모르는 채로 코드를 복사하면 **버그가 났을 때 어디를 봐야 할지 모르게 된다.**

### 2.1 인코더 · 파인튜닝 — 한 줄씩

| 용어 | 한 줄 설명 |
|---|---|
| **인코더** | 문장을 읽어 **토큰마다 벡터**를 뽑는 모델. 새 문장을 쓰지는 못한다. 우리 작업은 "어디에 무엇이 있나"라 생성이 필요 없어서 인코더로 충분하고, 그래서 1.1억 파라미터로 CPU 300ms가 가능하다 |
| **파인튜닝** | 이미 한국어를 배운 모델 위에 **우리 라벨을 얹어 다시 학습**시키는 것. 백지에서 학습하지 않는다 |
| **full fine-tuning** | 모델 **전체 가중치**를 갱신하는 방식. 110M이라 3060에서 여유가 있다. (D의 Qwen3-4B는 이게 불가능해서 QLoRA — 4bit로 압축해 얼려두고 작은 어댑터만 학습하는 방식 — 을 쓴다) |
| **에폭 / 배치 / 학습률** | 에폭 = 데이터를 몇 바퀴 도는가. 배치 = 한 번에 몇 개를 보고 가중치를 고치는가. 학습률 = 한 번에 얼마나 크게 고치는가 (**너무 크면 발산, 너무 작으면 안 배운다**) |
| **seqeval** | BIO 태그 리스트 두 개(정답·예측)를 넣으면 **스팬 단위** 정밀도·재현율·F1을 내주는 라이브러리. 우리가 쓸 채점기다 |

### 2.2 BIO 태깅 — 구간을 토큰 라벨로 바꾸는 약속

**문제**: 우리가 원하는 출력은 *구간*("12번째 글자부터 17번째 글자까지가 지역")인데, 인코더가 뱉는 것은 *토큰마다 라벨 하나*다. 이 간극을 메우는 표기법이 BIO다.

```
문장    집   근처   라   자주  가는   신갈  ##저수지  조황  입니다
BIO   B-REL I-REL   O    O    O    B-LOC  I-LOC     O     O
```

| 태그 | 뜻 |
|---|---|
| `B-유형` | **B**egin — 그 유형 구간의 **첫** 토큰 |
| `I-유형` | **I**nside — 같은 구간의 **이어지는** 토큰 |
| `O` | **O**utside — 아무 구간에도 속하지 않음 |

라벨 개수 = **유형 수 × 2 + 1**. 유형이 8개면 라벨은 17개다.

**왜 B와 I를 굳이 나누나.** 같은 유형의 구간이 붙어 있을 때 구분하려고. "신갈저수지 기흥호수"가 나란히 나오면 `B-LOC I-LOC B-LOC I-LOC` 이어야 **두 개**로 읽힌다. 유형만 붙이면(IO 태깅) 하나의 긴 구간으로 합쳐지고, 그러면 C의 특정성 계산에 시설이 하나만 넘어간다 — **"신갈저수지 + 기흥호수 두 개로 거주지가 좁혀졌다"는 우리 대표 사례가 사라진다.**

| ✗ 이렇게 하면 안 되고 | ○ 이렇게 한다 | 왜 |
|---|---|---|
| 문장 단위 "단서 있음/없음" 분류 | **토큰 단위 BIO 태깅** | 어디를 고쳐야 하는지 알려줘야 D의 리라이트·가명화가 가능하다 |
| B/I 구분 없이 유형만 (IO 태깅) | **B/I 구분** | 인접한 두 구간이 하나로 합쳐진다 |
| 라벨 위치를 **토큰 인덱스**로 저장 | **문자 offset (start, end)** | 토크나이저를 바꾸면 인덱스가 전부 어긋난다. 코퍼스는 살아남고 토크나이저는 바뀐다 |
| 스팬이 겹치게 라벨 | **겹침 규칙을 스키마에 못 박는다** | 아래 ⚠️ |

> ⚠️ **BIO는 겹치는 스팬을 표현할 수 없다.** 한 토큰에 라벨이 하나뿐이기 때문이다. "집 근처 신갈저수지" 전체를 거주 단서로 잡으면서 동시에 "신갈저수지"를 시설로 잡는 것은 **한 시퀀스로는 불가능하다.** 태그 시퀀스를 두 벌 학습하면 되지만 12주에 감당할 일이 아니다.
>
> → **A와의 라벨 스키마 합의에서 "겹침 금지 · 최장 우선"을 B가 먼저 제안한다.** 이건 취향이 아니라 모델 구조에서 나오는 제약이고, **A가 이 사실을 모르는 채로 겹침 허용 스키마를 만들면 코퍼스를 다시 라벨해야 한다.** W2 월~화 회의의 첫 안건이다.

**서브워드 문제.** 한국어는 조사가 붙는다. "신갈저수지에서"를 토크나이저는 `신갈` `##저수지` `##에서` 로 쪼갤 수 있는데, 우리가 원하는 스팬은 "신갈저수지"까지다. 토큰 경계와 스팬 경계가 어긋나는 것이 **한국어에서는 예외가 아니라 기본**이다. 실무 처리는 [howto/b-finetune.md §3](howto/b-finetune.md)에 있다.

### 2.3 스팬 F1은 문장 분류 정확도와 완전히 다르다

**정확도로 보고하면 숫자가 거짓말을 한다.**

글 200편에 토큰이 20,000개 있고 그중 단서 토큰이 600개(3%)라 하자. **아무것도 안 잡고 전부 `O`로 찍는 모델**을 상상해 보라.

| | 문장 분류 정확도 | 토큰 정확도 | **스팬 F1** |
|---|---|---|---|
| 세는 단위 | 문장 | 토큰 | **구간** |
| 전부 `O`로 찍는 모델 | 0.8~0.9 | **0.97** | **0.00** |
| 우리가 리포트에 쓸 것 | ✗ | ✗ | **○** |

토큰 정확도 0.97은 **아무것도 안 한 모델의 점수**다. 그래서 이 프로젝트의 모든 수치는 **스팬 F1**으로 낸다. 표기 사전([glossary.md](../glossary.md))이 *"정확도"라고 쓰지 말고 F1 또는 재현율이라고 쓰라*고 한 이유가 이것이다.

**계산 방법 — 정확 일치 기준**

```
정답 스팬:  (12, 17, LOC_FACILITY)   (25, 29, AGE)
예측 스팬:  (12, 17, LOC_FACILITY)   (30, 33, JOB)

TP = 1   (12,17,LOC_FACILITY 하나만 완전히 일치)
FP = 1   (30,33,JOB — 정답에 없다)
FN = 1   (25,29,AGE — 못 잡았다)

정밀도 = TP/(TP+FP) = 1/2 = 0.50
재현율 = TP/(TP+FN) = 1/2 = 0.50
F1     = 0.50
```

**정확 일치**는 시작·끝·유형이 **전부** 같아야 TP다. 한 글자만 어긋나도 FP와 FN이 **둘 다** 늘어난다(이중 페널티). 그래서 정확 일치 F1은 체감보다 낮게 나온다 — 놀라지 말 것.

**두 가지를 함께 낸다.**

| 기준 | 뜻 | 용도 |
|---|---|---|
| **정확 일치 F1** | 시작·끝·유형 완전 일치 | **대표 수치.** plan.md §10의 `≥ 0.80`은 이것이다 |
| 부분 일치(겹침) F1 | 구간이 겹치고 유형이 같으면 TP | 참고. "신갈저수지"를 "저수지"로만 잡았을 때 |

> ⚠️ **어느 기준인지 안 밝히면 부풀린 수치로 읽힌다.** 리포트의 모든 F1 옆에 *(정확 일치)* 를 적는다.

**등급별로 쪼갠다.** `explicit` / `implicit` / `inferential` 을 하나의 F1으로 뭉치면 목표 판정이 안 된다 — 명시는 `≥ 0.80`이고 암묵은 IAA 기준이라 **목표치 자체가 다르기 때문**이다. 처음부터 등급별로 내는 스크립트를 짠다.

**재현율을 항상 함께 적는다.** plan.md §4 설계원칙 3은 *"탐지기의 목표는 맞히기가 아니라 놓치지 않기"* 다. 방어 도구는 못 잡는 게 잘못 잡는 것보다 나쁘다. F1만 적으면 이 원칙이 숫자에서 사라진다.

## 3. ⭐ 베이스라인 3종 — 프로젝트의 중단 기준

**학습보다 먼저 한다.** W2에 착수, W3에 수치를 확정한다.

### 3.1 무엇을 돌리나

「3종」은 **하한 · 기존 도구 · 상한**의 세 갈래를 말한다. 기존 도구 칸에 두 개가 들어가므로 **실제로 돌리는 프로그램은 4개**다.

| 갈래 | 무엇 | 역할 | 기대 |
|---|---|---|---|
| **규칙 기반** | 정규식으로 주민번호·전화·이메일·계좌 | 성능의 **하한** | 명시 PII만, 암묵 0 |
| **기존 도구 ①** | Microsoft Presidio | **우리가 이겨야 할 대상** | 명시 PII 위주 |
| **기존 도구 ②** | korean-pii (또는 대체 한국어 도구) | 동일 | 동일 |
| **LLM 직접** | 좋은 AI에게 그냥 물어보기 | 성능의 **상한** | 암묵까지 상당수 |

> 💡 **LLM 상한 측정은 규칙 위반이 아니다.** RULES-DO-NOT #2의 표에서 *"평가 상한 / 합성 코퍼스 / 제약 없음"* 행에 해당한다. `.env`의 `ALLOW_EXTERNAL_LLM=false`는 **런타임에 사용자 글을 보내는 것**을 막는 스위치이지, 합성 코퍼스에 대한 오프라인 실험을 막는 것이 아니다. 혼동하기 쉬우니 실험 README에 한 줄 적어둔다.

**설치·실행 절차는 [howto/b-baselines.md](howto/b-baselines.md)에 있다.** 명령어, 정규식 목록, 출력 형식 통일, 계산 스크립트까지.

### 3.2 공정하게 돌려야 한다 — 여기서 반칙하면 전부 무효다

**Presidio의 기본 설정은 영어를 전제한다.** 그대로 한국어에 돌리면 당연히 못 잡는다. 그 결과를 "격차"라고 부르면 **심사에서 가장 먼저 깨진다.**

| ✗ | ○ |
|---|---|
| 기본 설정으로 돌리고 "못 잡았다"고 적는다 | **한국어 설정을 붙여 최선을 다한 뒤**에 잰다 |
| 설정을 리포트에 안 적는다 | **어떤 NLP 엔진·모델·버전으로 돌렸는지 전부 적는다** |
| 설정이 안 돼서 못 돌렸는데 "탐지 성능이 낮다"고 적는다 | *"한국어 환경 설정이 어려웠다"* 와 *"탐지를 못 한다"* 를 **분리해서 적는다** |

설정이 끝내 안 되면 **그 사실 자체가 결과다** — "한국어 환경에서 즉시 사용 가능하지 않다"는 것도 기존 도구의 한계다. 다만 성능 수치로 바꿔 적으면 안 된다.

### 3.3 「기존 도구 대비 추가 탐지율」을 어떻게 재나

**정의를 먼저 못 박는다.** 이 숫자가 중단 기준([roadmap.md §5](../roadmap.md))이므로 나중에 정의를 바꾸면 게이트 자체가 무의미해진다.

```
추가 탐지율 =  기존 도구가 놓쳤고 우리가 잡은 스팬 수
              ─────────────────────────────────────
                  기존 도구가 놓친 스팬 수
```

- **분모** = 골드셋 스팬 중 기존 도구 3종 중 **아무도** 잡지 못한 것
- **분자** = 그중 우리가 잡은 것
- 정확 일치 기준으로 센다. 절대 개수도 함께 적는다 (`분자/분모 = 87/143 = 60.8%`)

**여기 함정이 하나 있다.** W3 시점에는 **우리 모델이 아직 없다.** 학습은 W4~W5다. 그래서 W3에 잴 수 있는 것과 W7에 확정하는 것이 다르다.

| 시점 | 이름 | 무엇을 재나 | 산출 |
|---|---|---|---|
| **W2** | **미탐 목록** | 20편을 손으로 보고, 기존 도구 3종이 아무도 못 잡은 준식별자 구간을 나열 | 정성 목록 (수치 아님) |
| **W3** ⭐ | **미탐 공간 크기** | 골드셋 기준 — 기존 도구가 놓친 스팬이 **전체의 몇 %인가** | 중단 기준 판정용 |
| **W3** ⭐ | **도달 가능성** | 그 미탐 공간에서 **LLM 상한이 잡는 비율** | 학습으로 도달 가능한지 |
| **W7** | **추가 탐지율 (확정)** | 우리 모델 v1이 미탐 공간에서 잡는 비율 | 최종 리포트 |

**W3 판정 논리**: 미탐 공간이 넓고(분모가 크고) LLM 상한이 그 안에서 잘 잡으면(학습 신호가 존재하면) → **주제가 성립한다.** 미탐 공간이 애초에 좁으면 → 기존 도구로 충분하다는 뜻이고, 우리가 아무리 잘 만들어도 의미가 없다.

> ⚠️ [roadmap.md §5](../roadmap.md)는 중단 기준을 *"W3에 측정하는 「기존 도구 대비 추가 탐지율」"* 이라고 적었다. 위 분해가 그 문장을 **측정 가능한 형태로 쪼갠 것**이다. 정의를 조용히 바꾸는 게 아니라 **W2에 PM·멘토에게 확인받고 실험 README에 박아둔다.**

**등급별로 쪼개서 낸다.** 이게 진짜 하고 싶은 이야기다.

| 등급 | 예상 | 이게 보여주는 것 |
|---|---|---|
| `explicit` | 기존 도구가 **잘 잡는다** | 우리가 이기려는 영역이 아니다 |
| `implicit` | 기존 도구가 **못 잡는다** | ← 우리 존재 이유 |
| `inferential` | 기존 도구가 **거의 못 잡는다** | ← 우리 존재 이유 |

등급을 뭉쳐서 하나의 숫자로 내면 이 서사가 사라진다.

### 3.4 격차가 안 보이면

> ⚠️ **즉시 팀에 알린다. 숨기고 다음 주에 다시 재보지 않는다.** W4 설계서에서 주제 재검토 여부를 판정해야 하므로, 늦게 알리면 판정할 시간이 없어진다.

다만 **"격차가 explicit에는 없다"는 것은 나쁜 결과가 아니다.** 오히려 주제를 정확히 좁히는 근거다 — *"명시 PII는 이미 해결됐고 준식별자가 남았다"* 가 우리 주장이기 때문이다. 정말로 위험한 결과는 **implicit·inferential에서도 기존 도구가 다 잡는 경우**다.

**왜 격차가 있을 거라고 보나.** 기존 도구는 *형식이 있는 것*을 찾는다 — 숫자 패턴, 이메일 모양, 사전에 등록된 이름. 그런데 "신갈저수지"는 그냥 지명이고, "마흔여덟"은 숫자도 아니다. 선행 PoC 자체 측정에서 **명시적 개인정보를 전부 지운 뒤에도 신상 7속성이 그대로 추론됐다**(암묵-only ablation: R1 위험도 76.1 → 66.0, R3 82.8 → 69.9, 속성 적중은 7/7 유지).

## 4. ⚠️ 위험도는 학습 대상이 아니다

가장 헷갈리는 지점이라 먼저 짚는다.

**이 모델은 "이게 위험하다"를 배우지 않는다.** "이건 지역 단서다"까지만 배운다.

왜냐면 **같은 표현의 위험도가 문맥마다 다르기 때문**이다. "신갈저수지"는 단독으로는 무해하다. "기흥호수"와 함께 나와야 거주지가 된다. 같은 단어에 문맥마다 다른 위험도를 라벨하면 정답이 일관되지 않고, 그러면 성능 지표 자체가 무의미해진다.

| 누가 | 무엇을 담당 |
|---|---|
| **B (나)** | "이 구간은 지역 단서다" — **문맥과 무관하게 일관된 라벨** |
| C | "이 조합이면 몇 명으로 좁혀지나" — 위험도 계산 |
| D | "따라서 이 사람은 어디 산다" — 종합 판정 |

**실무에서 이게 뜻하는 것**: 라벨 스키마에 `risk`, `score`, `severity` 같은 필드를 넣자는 말이 나오면 **거절한다.** 스팬에 붙는 것은 `type`과 `level`(등급)까지다. 신뢰도 `score`는 모델이 뱉는 확률값이지 위험도가 아니다.

### 4.1 밈·유행어는 모델이 아니라 사전이다 — 이것도 1단의 몫

[plan.md §4](../plan.md)는 1단이 하는 일을 *"스팬 탐지(BIO) · **문체/세대 신호 · 밈 사전 매칭** · 특정성 · 기여도"* 로 적었고, 설계원칙 4가 그 처리 방식을 못 박았다.

> **밈·유행어는 모델이 아니라 사전(시그니처 DB)으로 잡는다 — 파일 교체로 갱신, 재학습 불필요.**

**왜 학습시키지 않나.** *"~하는 중"*, *"레게노"*, *"ㅇㅈ?"* 같은 표현은 **세대 추정의 강한 신호**지만 6개월이면 바뀐다. 모델에 태워 학습하면 유행어 하나 추가할 때마다 재학습이고, 코퍼스도 그 시점 유행어에 고정된다. 사전은 **JSON 한 줄 추가로 끝난다.**

| 항목 | 내용 |
|---|---|
| 파일 | `data/dict/signatures/meme.json` — **B 소유.** 모델 체크포인트와 독립적으로 갱신 |
| 형식 | `{"표현": {"axis": "age", "hint": "10~20대", "confidence": 0.4}}` |
| 출력 | 매칭 결과도 **`span.schema.json` 그대로** 나간다. 모델 예측과 섞이지 않게 유형을 따로 둔다(예: `MEME_GEN`) |
| 유형 등록 | 이 유형을 `label-schema.md`의 유형 목록에 넣을지 **W2에 A와 함께 정한다** — 안 넣으면 골드셋에 정답이 없어 채점이 안 된다 |
| 채점 | 사전 매칭은 **모델 F1과 분리해서** 보고한다. 섞으면 모델 성능이 사전 덕에 부풀려진다 |

> ⚠️ 사전 항목은 **`confidence`를 낮게** 잡는다. 유행어는 세대를 *암시*할 뿐 확정하지 않는다. C가 §4 규칙 3의 신뢰도 가중에 그대로 쓴다.

## 5. 모델과 학습 방법

| | 내용 |
|---|---|
| **모델** | KoELECTRA-base (`monologg/koelectra-base-v3-discriminator`, 약 1.1억 파라미터) |
| **방식** | full fine-tuning — 모델 전체를 우리 데이터로 다시 학습 |
| **작업 형태** | 토큰 분류(token classification) · BIO 태깅. 문장 분류가 아니다 |
| **비교 후보** | KLUE-RoBERTa, KoBERT — 여유가 있으면 |
| **소요** | RTX 3060 12GB에서 배치 32 · seq 256으로 **수 시간** |

**KoELECTRA를 주력으로 정한 이유**: 한국어 개체명 인식 벤치마크에서 우세하다는 문헌이 있고, 4주차 설계서에 모델을 확정해서 써야 하는데 비교 실험을 기다릴 시간이 없다. 비교는 여유 시에 한다.

### 하이퍼파라미터 출발점

**여기서 시작해서 조금씩 움직인다.** 처음부터 탐색하지 않는다 — W4에 그럴 시간이 없다.

| 항목 | 출발값 | 움직이는 방향 |
|---|---|---|
| 학습률 | `3e-5` | 손실이 튀면 `2e-5` → `1e-5`. 아예 안 내려가면 `5e-5` |
| 에폭 | `3` | 과적합이면 2, 덜 배웠으면 5까지 |
| 배치 | `16` | VRAM이 남으면 32. 부족하면 8 + gradient accumulation |
| max_length | `256` | 글이 잘리면 384~512 (VRAM은 길이 제곱에 가깝게 늘어난다) |
| warmup 비율 | `0.1` | 초반 발산 방지 |
| weight decay | `0.01` | 거의 안 건드린다 |
| 정밀도 | `fp16` (또는 `bf16`) | `nan`이 뜨면 §10.2 |
| 시드 | **고정하고 기록** | 재현성이 곧 증빙이다 |

**실무 절차는 [howto/b-finetune.md](howto/b-finetune.md)에 있다** — 데이터 로더, 서브워드 정렬, 학습 루프, 평가, 체크포인트 재개, 추론 함수, 지연 측정까지.

### GPU가 없거나 부족하면

학습 데이터가 전부 합성이라 **클라우드에서 돌려도 문제없다.** 로컬이어야 하는 건 *사용자 글을 다루는 추론*이지 학습이 아니다.

| 순위 | 수단 | 주의 |
|---|---|---|
| 1 | 본인 RTX 3060 | 기본 |
| 2 | AWS 크레딧 | **루트 액세스키 금지 · Budgets 알림 필수** (RULES #7). 인스턴스 상시 기동이 사고 1순위 |
| 3 | Kaggle 무료 GPU (주 30시간) | 세션이 끊긴다 → **중간 저장 후 이어서 학습**을 처음부터 전제로 짠다 |

## 7. 목표 수치 — 그리고 어떻게 재나

| 지표 | 목표 | 계층 | 재는 법 |
|---|---|---|---|
| 스팬 F1 (**명시** 단서) | **≥ 0.80** | 필수 | 정확 일치 · 골드셋 · seqeval |
| 글 1건 탐지 지연 (CPU) | **< 300ms** | 필수 | 아래 §7.1 |
| 스팬 F1 (**암묵** 단서) | **사람끼리 일치도의 80% 이상** | 목표 | A의 IAA 측정치를 상한으로 삼는다 |
| 기존 도구 대비 추가 탐지율 | **> 0** | 목표 ⭐ | §3.3 |

**암묵 F1에 고정 숫자를 쓰지 않는 이유**: "무릎이 예전 같지 않네요"가 나이 단서인지는 **사람 둘이도 갈린다.** 사람이 0.55밖에 못 맞추는 문제에서 모델에게 0.60을 요구하는 건 말이 안 된다. 그래서 A가 W3에 측정하는 **사람끼리의 일치도(IAA)를 상한으로 놓고** 그 80%를 목표로 삼는다. plan.md §10의 `≥ 0.60`은 **M1 IAA 측정치로 재조정한다**고 이미 명시되어 있다.

### 7.1 CPU 지연을 재는 절차

**사용자 컴퓨터에 GPU가 있다고 가정할 수 없다.** 실제 사용 환경 기준으로 잰다.

| 조건 | 값 | 왜 |
|---|---|---|
| 장치 | **CPU 강제** | GPU로 재면 무의미하다 |
| 배치 | **1** | 사용자는 글 하나를 쓴다 |
| 측정 범위 | **토크나이즈 + 추론 + 후처리(BIO→스팬) 전부** | 모델 forward만 재면 실제보다 빠르게 나온다 |
| 워밍업 | 5회 버리고 시작 | 첫 호출이 유난히 느리다 |
| 표본 | 50회의 **중앙값** | 평균은 이상치에 흔들린다 |
| 스레드 수 | 고정하고 **기록** | 안 적으면 재현이 안 된다 |
| 입력 길이 | **대표 글 1편** (코퍼스 중앙값 길이) | 짧은 글로 재면 반칙이다 |

300ms를 못 맞추면 폴백 사다리가 있다 → §11.

## 8. 다른 역할과 주고받는 것

| 상대 | 내가 주는 것 | 내가 받는 것 |
|---|---|---|
| **A** 이은선 | 라벨 스키마 의견 (같이 정한다) · **겹침 불가 제약** | 라벨된 코퍼스, 골드셋, blind 200, IAA 수치 |
| **C** 신정현 | 탐지된 스팬 + 유형 | 어떤 유형 구분이 위험도 계산에 필요한지 |
| **D** 박재현 | 스팬·유형 (2단과 triage의 입력이 된다) | — |
| **E** 이지희 | 모델 파일 + **추론 함수** | 통합 인터페이스 규격 |

**출력 형식은 W2 목요일에 고정된다.** C와 D가 내 출력을 입력으로 쓰므로, 형식이 늦게 정해지면 셋이 서로 기다린다. 목요일 머지 후에는 변경에 2명 승인이 필요하다(CODEOWNERS).

```json
{
  "schema_version": "1.0",
  "post_id": "S01_b07",
  "model_version": "koelectra-base-v3-ft-20260921",
  "spans": [
    {"start": 12, "end": 17, "text": "신갈저수지",
     "type": "LOC_FACILITY", "level": "inferential", "score": 0.91}
  ]
}
```

> `schema_version`은 계약 4종 전부에 들어간다(E). `model_version`은 RULES-DO-NOT #9(모든 수치에 모델 버전)을 출력 자체로 만족시키는 필드다 — **E의 스키마 초안에 이 두 필드가 있는지 W2 1:1에서 확인한다.**

**계약에 반드시 못 박을 것 네 가지** — 나중에 바꾸기 제일 어려운 것들이다.

| 항목 | B의 입장 | 이유 |
|---|---|---|
| 위치 기준 | **문자 offset** (`start` 포함, `end` 미포함) | 토크나이저가 바뀌어도 살아남는다. `end` 포함/미포함을 안 정하면 한 글자씩 어긋난다 |
| 겹침 | **금지 · 최장 우선** | BIO 구조 제약 (§2.2) |
| 관계어 | **별도 유형** (`REL_HOME`, `REL_COMMUTE` 등) | "집 근처"·"퇴근하고"가 시설명을 거주 단서로 바꾼다. LOC에 합치면 C가 그 구분을 못 쓴다 ← **제안이고, A·C와 합의해서 확정한다** |
| `score` | **모델 확률값**. 위험도가 아니다 | §4 |

## 9. 데이터가 아직 없을 때 — 먼저 할 수 있는 것

A의 코퍼스는 W2에 200편, 골드셋은 W3다. **기다리지 않는다.**

| 없는 것 | 그동안 할 것 |
|---|---|
| 라벨된 코퍼스 | **가짜 데이터 20건**을 손으로 만들어 파이프라인을 완성한다. 형식만 맞으면 나중에 그대로 교체된다 |
| 골드셋 | W2 비교는 **손으로 20편 눈으로 보는 것**으로 충분하다. 목표는 수치가 아니라 *"기존 도구가 무엇을 놓치는지"* 확인 |
| 최종 유형 목록 | 임시로 3~4개(`LOC_FACILITY` `AGE` `JOB`)만 두고 짠다. 유형 수는 `label2id` 딕셔너리 하나만 고치면 바뀐다 |

이렇게 하면 코퍼스가 도착한 날 **학습을 그날 시작할 수 있다.**

## 10. 막히기 쉬운 지점

### 10.1 GPU 메모리가 부족할 때

`CUDA out of memory`는 정상적인 일이다. **위에서부터 하나씩** 적용하고, 적용한 것을 실험 README에 적는다.

| 순서 | 조치 | 효과 | 대가 |
|---|---|---|---|
| 1 | `max_length` 512 → **256** | 큼 (길이에 제곱 가깝게) | 긴 글이 잘린다 — 잘린 비율을 세어 기록 |
| 2 | 배치 32 → **16 → 8** | 비례 | 학습이 느려진다 |
| 3 | `gradient_accumulation_steps` 로 **유효 배치 복원** | — | 배치 8 × accum 4 = 유효 32. **없음** |
| 4 | `fp16=True` (또는 `bf16=True`) | 큼 | fp16은 발산 위험 → §10.2 |
| 5 | `gradient_checkpointing=True` | 큼 | **학습 속도 20~30% 손해** |
| 6 | 평가 배치를 학습 배치보다 작게 | 중간 | 평가만 느려진다 |
| 7 | 클라우드로 이전 | — | 합성 데이터라 문제없다 |

> 💡 **에러가 학습 도중이 아니라 평가 시점에 난다면** 평가 배치가 원인이다. `per_device_eval_batch_size`를 따로 줄인다. 흔한 함정이다.
>
> 💡 **다른 프로세스가 VRAM을 잡고 있는지 먼저 본다.** `nvidia-smi`. 주피터 커널이 살아 있는 경우가 대부분이다.

### 10.2 학습이 발산하거나 아무것도 안 배울 때

**먼저 어느 쪽인지 구분한다.** 대처가 정반대다.

| 증상 | 진단 | 조치 |
|---|---|---|
| 손실이 `nan` | **발산** | 학습률 ↓ (`3e-5`→`1e-5`) · warmup 늘리기 · `max_grad_norm=1.0` · **fp16을 bf16 또는 fp32로** (fp16 오버플로가 흔한 원인) |
| 손실이 널뛴다 | 발산 직전 | 학습률 ↓ · 배치 ↑ |
| 손실은 잘 내려가는데 **F1이 0** | **라벨 정렬 버그** ← 가장 흔하다 | 아래 ⭐ |
| 손실이 거의 안 움직인다 | 안 배움 | 학습률 ↑ (`3e-5`→`5e-5`) · 라벨이 전부 `O`인지 확인 |
| 학습 F1은 높은데 평가 F1이 낮다 | 과적합 | 에폭 ↓ · 데이터 ↑ · 조기 종료 |

> ⭐ **"손실은 내려가는데 F1이 0"은 거의 항상 라벨 정렬 버그다.** 모델이 전부 `O`로 찍으면 손실은 잘 내려간다(토큰의 97%가 정답이니까). 그런데 스팬은 하나도 안 나오니 F1은 0이다.
>
> **1분 진단법**: 학습 데이터 한 건을 꺼내 `labels`에서 `-100`과 `O`를 뺀 나머지가 몇 개인지 센다. **0이면 정렬이 깨진 것이다.**
>
> **확실한 진단법 — 100건 과적합 테스트**: 학습 데이터 100건으로 학습하고 **같은 100건으로** 평가한다. F1이 0.9 이상 나와야 정상이다. 안 나오면 모델이 아니라 **데이터 파이프라인**이 잘못됐다. 전체 학습을 돌리기 전에 이 테스트를 먼저 통과시킨다 — 몇 분이면 끝나고, 며칠을 아낀다. 절차는 [howto/b-finetune.md §5](howto/b-finetune.md).

### 10.3 O 태그가 압도적으로 많을 때

A의 코퍼스는 **노이즈가 70~80%** 다(설계상 그렇게 만든다). 여기에 문장당 단서는 한두 개뿐이라, 토큰의 **95~98%가 `O`** 가 된다. 정상이다.

| 대처 | 방법 | 언제 |
|---|---|---|
| **① 정확도 대신 스팬 F1을 본다** | seqeval | **항상.** 사실 이게 대부분의 답이다 |
| ② class weight | 손실 함수에서 `O`의 가중치를 낮춘다 | 재현율이 목표에 못 미칠 때 |
| ③ 학습셋에서 전부-`O` 문장 일부 제외 | 샘플링 | 학습이 너무 느릴 때 |
| ④ focal loss | 쉬운 예제의 기여를 줄인다 | ②로 부족할 때. 우선순위 낮음 |

> ⚠️ **③을 쓸 때: 학습셋에서만 뺀다. 평가셋에서는 절대 빼지 않는다.**
> A가 네거티브 컨트롤을 전체의 10~15% 넣어둔 이유가 **과탐 억제**다(plan.md §6). 평가에서 무단서 글을 빼면 정밀도가 부풀려지고, 네거티브 컨트롤이라는 방어 하나가 통째로 무력해진다.

**재현율 중심 조정**: 목표는 "놓치지 않기"다(plan.md §4 원칙 3). ②로 `O` 가중치를 낮추면 재현율이 오르고 정밀도가 내려간다. **F1이 조금 떨어져도 재현율이 오르는 쪽을 택할 수 있다** — 다만 그 판단을 실험 README에 적는다.

### 10.4 그 밖에

| 상황 | 대처 |
|---|---|
| 암묵 단서 F1이 너무 낮다 | **정상일 수 있다.** IAA와 비교해서 판단한다. 사람도 못 맞추는 문제면 목표를 낮추는 게 맞다 |
| 기존 도구 대비 격차가 안 보인다 | **즉시 팀에 알린다.** 숨기면 안 된다. 프로젝트 방향 판정이 여기 걸려 있다 (§3.4) |
| Presidio가 한국어에서 안 돌아간다 | [howto/b-baselines.md §4](howto/b-baselines.md)의 3단계 폴백. **끝내 안 되면 그 사실을 결과로 기록**하되 성능 수치로 바꾸지 않는다 |
| korean-pii가 설치가 안 된다 | 대체 한국어 도구로 바꾸고 **바꾼 이유를 적는다.** 기존 도구 칸이 비면 안 된다 |
| `return_offsets_mapping`에서 에러 | fast 토크나이저가 아니다. `AutoTokenizer.from_pretrained(..., use_fast=True)` 확인 |
| Kaggle 세션이 끊긴다 | 중간 저장 → 이어서 학습 구조를 **처음부터 전제로** 짠다 |
| 파인튜닝을 해본 적이 없다 | HuggingFace 토큰 분류 패턴이 거의 그대로 쓰인다. **데이터 형식만 맞추면** 나머지는 정형화되어 있다 → [howto/b-finetune.md](howto/b-finetune.md) |
| 라이브러리 API가 문서와 다르다 | transformers는 버전마다 인자 이름이 바뀐다(예: `evaluation_strategy` ↔ `eval_strategy`). **에러 메시지가 알려준다.** 설치 버전을 `requirements.txt`에 고정한다 |

## 11. 실패해도 되는 곳 — 폴백 지도

**전부 성공해야 하는 자리가 아니다.** 어디까지 실패해도 프로젝트가 서는지 미리 적어둔다.

| 실패한 것 | 폴백 | 잃는 것 | 프로젝트 영향 |
|---|---|---|---|
| 로컬 GPU 학습 | AWS → Kaggle | 시간 | **없음** — 합성 데이터라 클라우드 가능 |
| 300ms 미달 | ① max_length 축소 ② 동적 양자화(int8) ③ ONNX Runtime ④ 더 작은 백본 | 양자화 시 F1 소폭 하락 → **양자화 후 F1을 다시 잰다** | 필수 지표라 사수 |
| 암묵 F1이 목표 미달 | IAA 대비 비율로 보고 | 절대 수치 | **없음** — 목표 정의가 이미 상대값이다 |
| KoELECTRA가 기대에 못 미침 | KLUE-RoBERTa로 교체 | 재학습 시간 | 작음 — 코드는 백본 이름만 바꾸면 된다 |
| korean-pii 설치 실패 | 대체 한국어 도구 + 사유 기록 | 비교 대상 1종 | 작음 — Presidio가 주 비교 대상이다 |
| 벤치마크 러너 (W9~) | 스크립트 여러 개를 순서대로 실행 | 재현 편의 | 작음 |
| **기존 도구 대비 격차 없음** | 폴백 없음 | — | 🔴 **주제 재검토.** 이것만은 폴백이 없다 |

## 12. 모든 수치에 붙는 것

RULES-DO-NOT #9다. 예외 없다.

```
측정일 · 데이터 버전 · 모델 버전 · 하드웨어 · 시드 · 채점 기준(정확 일치/부분 일치)
```

**실험 하나당 폴더 하나**를 만든다. 양식은 [`experiments/_template/`](../../experiments/_template/)를 복사한다.

```
experiments/exp01-baseline/
├─ README.md              무엇을 왜 재는가 · 설정 · 결과 · 해석 · 한계
└─ results/metrics.json   수치만 커밋 (원문·중간산출물은 커밋하지 않는다)
```

커밋 타입은 **`exp`** 를 쓴다. `git log --grep='^exp'` 한 줄이 8주차 「학습·테스트 진행 내용」이 되기 때문이다.

```
exp(c1): 베이스라인 3종 측정 — 기존 도구 미탐 공간 62%, LLM 상한이 그중 71% 회수
exp(c1): KoELECTRA-base 파인튜닝 1차 — 스팬 F1 명시 .84 / 암묵 .58 (정확 일치)
```

- [ ] W2에 라벨 스키마 합의 완료 — **겹침 규칙과 offset 기준이 문서에 적혀 있음**

- [ ] 기존 도구 대비 추가 탐지율이 **정의와 함께** 숫자로 나옴
- [ ] 스팬 F1(명시, **정확 일치**) **≥ 0.80**
- [ ] 글 1건 CPU 추론 **< 300ms** — 측정 절차(§7.1)를 따랐고 하드웨어가 적혀 있음
- [ ] 암묵 F1이 IAA 대비 몇 %인지 산출됨
- [ ] F1과 **재현율**을 함께 보고함
- [ ] 모든 수치에 **측정일 · 데이터 버전 · 모델 버전 · 채점 기준**이 붙음
- [ ] 체크포인트가 repo에 없고 `models/registry.md`에 포인터가 있음
- [ ] E가 내 모델을 불러 쓸 수 있는 추론 함수 제공
- [ ] 학습에 쓴 외부 코퍼스의 **라이선스가 기록됨** (공개 가능 여부가 걸려 있다)
- [ ] W7까지 성능 리포트 완료 (중간점검보고서 마감이 W8)

## 0. 이 역할이 없으면 무슨 일이 생기나

**아무것도 안 보인다.**

A·B·C·D가 만드는 건 전부 부품이다. 데이터, 모델, 계산 엔진 — 심사위원 앞에서 보여줄 수 있는 형태가 아니다. **그걸 화면으로 만들고 하나로 연결하는 게 이 자리**다.

그리고 하나 더 — 개인정보 트랙이라서 **"법적으로 이게 무슨 의미인가"에 답하지 못하면 프로젝트가 반쪽이 된다.** 그 답을 준비하는 것도 이 자리다.

**코딩 부하는 다섯 자리 중 가장 낮은 편**이다. 대신 계속 조금씩 바쁘고, 문서를 읽는 일이 많다.

## 1. 세 덩어리를 만든다

### ① 가상 SNS 플랫폼 (⑦)

글을 쓰고 올리는 SNS 형태의 웹 서비스. 네이버 블로그·인스타그램 자리를 대신하는 **실험 환경**이다.

### ② 분석 웹앱 (⑥)

위험도를 보여주는 화면. 3화면으로 구성한다.

```
스캔                    진단                       조치
내 글 불러오기    →    "AI가 추정한 당신"    →    무엇을 어떻게 되돌릴지
위험도 0~100          7속성 + 근거 + 신뢰도       추천 + 사용자 선택
```

### ③ 컴플라이언스 (§13)

법령·가이드라인을 읽고 우리 설계를 정당화하는 문서.

## 2. ⚠️ 가장 중요한 설계 원칙 — 두 계층을 분리한다

이걸 어기면 **프로젝트의 핵심 논거가 무너진다.**

```
[가상 SNS 플랫폼]   ← 사용자 데이터가 원래 있는 곳의 "시뮬레이터"
      │                우리 제품이 아니다. 네이버 자리를 대신할 뿐
      │ 입력 어댑터
      ↓  { 글 목록 · 본문 · 작성시각 · 활동 메타 }
[분석 도구]          ← 이게 우리 제품. 사용자 측 실행. 외부 전송 0
```

**왜 이렇게까지 신경 쓰나.** 이 프로젝트의 주장은 *"프라이버시를 검사한다고 사용자 글을 외부로 보내면 그 도구 자체가 침해다"* 이다. 그런데 우리가 웹 서비스를 만들면서 사용자 글을 우리 서버에 모아두면 — **우리가 그 침해를 저지르는 셈**이 된다.

그래서 가상 SNS는 *플랫폼 자리*이고, 분석기는 *사용자 측에서 도는 것*으로 명확히 나눈다. 둘을 한 서버에 합치면 안 된다.

> **발표 때 결정타**: 스캔을 돌리면서 브라우저 개발자도구의 네트워크 탭을 열어 **외부로 나가는 요청이 0건**임을 보여준다. 말로 설명하는 것보다 훨씬 강하다. 이걸 염두에 두고 설계한다.

## 3. 가상 SNS — 무엇을 만드나

| 기능 | 왜 필요한가 | 주차 |
|---|---|---|
| 글 작성 · 목록 · 본문 조회 | 기본. 글 이력이 있어야 누적 위험을 시연할 수 있다 | W3 |
| 프로필 | 인물 구분 | W3 |
| **합성 코퍼스 자동 시딩** | A가 만든 글을 스크립트로 밀어넣기. 수작업 금지 | W4 |
| **수동 업로드 경로** | 텍스트 붙여넣기·파일. **실제 검증이 이 경로로 돈다** | W5 |
| **활동 메타** — 닉네임 · 위치태그 · 작성 시각 | ⭐ 실측에서 **"활동 메타 관리"가 위험도 감소 1위**였다. 이 필드가 없으면 핵심 메시지를 시연 못 한다 | W6 |
| 에디터 실시간 경고 | 글 쓰는 중에 *"이 표현이 이전 글의 ○○와 결합합니다"* | W9 |

**수동 업로드는 공수가 거의 0인데 가치가 크다.** M4의 외적 타당성 검증(동의받은 실제 블로거 대상)이 이 경로로 돌아가고, 참여자에게 프로그램 설치를 요구하지 않아도 된다.

**CRUD 수준이면 충분하다.** 화려할 필요 없고, 실제 SNS가 가진 구조(글 목록 / 본문 / 작성 / 프로필 / 메타)만 있으면 된다.

## 4. 컴플라이언스 — 무엇을 정리하나

**별도 워크스트림이 아니다. 설계를 정당화하는 근거로 쓴다.** W1에 한 번 정리하고, 이후에는 지표와 아키텍처에 녹아서 유지된다.

### W1에 정리할 것

**① k값을 법적 기준에 대응시키기** (C와 공동)

| k값 | 위험 등급 |
|---|---|
| k ≤ 2 | 매우 높음 |
| k = 3~4 | 높음 |
| k ≥ 5 | 통상 허용 수준 |

근거: 개인정보보호위원회 **가명정보 처리 가이드라인**의 적정성 검토 절차.
→ 점수가 *"우리가 정한 숫자"* 에서 *"규제 기준에 대응하는 숫자"* 가 된다.

**② 아키텍처가 규제 체계와 정렬됨을 보이기**

| 우리 구조 | 규제상 위치 | 우리 조치 |
|---|---|---|
| 1단 로컬 처리 (외부 전송 0) | 동일 처리자 내부 · **저위험** | 기본 경로 |
| 2단 외부 AI 전송 | 제3자 제공 · **중·고위험** | 명시적 동의 **+** 가명화 후 |

**③ 근거 법령 정리**

| 조항 | 우리 프로젝트에서의 의미 |
|---|---|
| 개인정보보호법 제2조 1호 나목 | *"다른 정보와 쉽게 결합하여 알아볼 수 있는 정보"* = **준식별자도 개인정보**. 결합 용이성은 입수 가능성·시간·비용·기술로 판단 → **AI가 그 문턱을 무너뜨렸다**는 것이 이 프로젝트의 법적 존재 이유 |
| 제2조 2호 | **수집도 처리행위** → 사후 마스킹이 무동의 수집을 치유하지 못함 |
| 제28조의2 | 가명정보 특례 — 추가정보 분리보관·재식별 금지 |
| 제33조 | 개인정보 영향평가(기업 의무) — **우리 진단 화면이 그 개인용 버전** |
| 대법원 2014다235080 | 공개된 개인정보도 이익형량 대상 — *"공개했으니 써도 된다"* 는 성립하지 않음 |

**④ AI 기본법 검토** (결론은 미정으로 둬도 된다)

인공지능 기본법이 2026년 시행되었다. 검토할 것: 우리 시스템이 고영향 AI에 해당하는지 / 연구·시제품 단계에 사업자 의무가 적용되는지 / 적용된다면 투명성 의무를 화면에 어떻게 반영할지.

> 참고로 우리 시스템은 이미 **근거 문장 제시 + 신뢰도 표기 + 근거 없을 때 기권**을 수행하므로 투명성 요구와 방향이 일치한다.

### M3~M4에 준비할 것

**동의 프로토콜** — 실제 블로거를 대상으로 한 검증용.

- 모집: 3년 이상 운영한 공개 블로그 보유자, 10~20명
- 동의서: 목적·범위·보관기간·파기 방법·철회권 명시
- 처리: **로컬 전용, 외부 전송 0.** 발표는 익명·집계만
- 파기: 분석 종료 즉시 원본·중간산출물 전부

> ⚠️ **미결 2건** — 연구윤리심의(IRB)가 필요한지, 그리고 동의자 글에 등장하는 **제3자·미성년 정보**(자녀·지인)를 어떻게 다룰지. 본인 동의로 커버되지 않는 영역이다. 멘토·지도교수 의견이 필요하다.

## 6. 인터페이스 계약 — W2에 정할 4가지

| 계약 | 누구와 | 내용 |
|---|---|---|
| **스팬 스키마** | B | 탐지 결과 형식 (구간 위치, 유형) |
| **특정성 스키마** | C | k값 입출력 |
| **기여도 스키마** | C | 글별 기여도, 조치 후 재계산 |

**여기에 계층 경계도 명시한다** — 플랫폼과 분석기가 무엇을 주고받는지, 무엇은 절대 넘기지 않는지.

## 8. 막히기 쉬운 지점

| 상황 | 대처 |
|---|---|
| 웹 개발을 많이 안 해봤다 | CRUD 수준이면 충분하다. 익숙한 프레임워크 아무거나 쓰면 된다 |
| 다른 사람 산출물이 안 와서 통합을 못 한다 | **가짜 데이터로 먼저 붙인다.** 형식만 맞으면 나중에 실제 모델로 교체된다. 기다리지 않는 게 핵심 |
| 인터페이스를 뭘 정해야 할지 모르겠다 | 완벽할 필요 없다. **나중에 바꾸기 어려운 것**(필드 이름, 좌표 기준, 단위)부터 정한다 |
| 법령 문서가 너무 길다 | 전문을 읽을 필요 없다. 위 표의 5개 조항과 가이드라인의 재식별 위험성 검토 절차만 보면 된다 |
| 두 계층 분리가 헷갈린다 | 판단 기준 하나: **"사용자 글의 원문이 우리 서버로 넘어가나?"** 넘어가면 잘못된 설계다 |
| 후반에 일이 몰린다 | 가상 SNS를 W3~W6에 앞당겨 배치한 게 그 대비다. **W6까지 플랫폼을 끝내두면** 후반이 훨씬 가볍다 |

## 외부 요청 0 — 측정 뒤 2계정 점검 동안의 TCP 연결

11/5 17:34 ~ 17:35 KST (08:34:16 ~ 08:35:45 UTC) · 촬영용으로 떠 있던 수정 KoELECTRA 분석기(위 `/api/engine-mode` 와 같은 프로세스)에서 쟀다. freeze-W12-gguf 와 같은 방식이다 — 시스템 TCP 연결을 0.2초마다 모으고(psutil 7.2.2) 우리가 띄운 프로세스만 골라 중복을 뺐다. 그동안 메인 · 예비 2계정을 촬영 경로(프록시 8080 `/check` · 빠른 결과 → 정밀 판정)와 한 번에 응답으로 한 번씩 돌렸다(둘 다 2단 `done` · `qwen3-4b-qlora-v2-gguf-q8-lora`). 실행 장소가 EC2 이므로 「외부 주소」는 루프백(127.0.0.1 · ::1) 밖 주소, 곧 인스턴스 밖 주소를 말한다.

| 프로세스 | 고유 연결 | 외부 주소 | 대기 소켓 |
|---|---:|---:|---|
| 분석기 + llama-server(자식) | 11 | **0** | `127.0.0.1:8000` · `127.0.0.1:8092` |
| 촬영용 프록시 | 9 | **0** | `127.0.0.1:8080` |
| Veilo | 2 | **0** | `127.0.0.1:3000` |
| 촬영용 터널(cloudflared) — 분석과 별개 | 1 | 0 (TCP) | `127.0.0.1:20241`(관리용) |

**분석기 · llama-server 의 외부 주소 연결: 0개.** llama-server 는 `127.0.0.1:8092` 에서만 대기했고, 연결 상대는 분석기(127.0.0.1)뿐이었다.

- 터널(cloudflared)에는 TCP 대기 소켓 하나와 원격 주소가 없는 UDP 소켓만 보였다. 이 감시로는 터널이 밖으로 나가는 연결의 목적지 · 프로토콜을 확인하지 못했다. 터널은 시청자 요청을 프록시로 넘기는 촬영 경로이고 분석 경로가 아니므로 위 「외부 0」과 따로 둔다
- 115계정 실행 중(05:10 ~ 08:30 UTC)에는 연결을 감시하지 않았다. 그 대신 분석기 로그를 셌다 — 「127.0.0.1 밖에서 온 요청」 v2 0건 · 수정 0건, 점검 요청(`POST /scan`)은 v2 · 수정 모두 하네스가 보낸 232건((115계정 + 워밍업 1회) × 2경로)과 같다

## 한계

- 인스턴스 한 대(멘토 EC2 · L4)에서 확인했다. 로컬 PC(RTX 3060) 결과는 freeze-W12-gguf(1단 v2)뿐이다
- 1단 교체의 정확도 근거와 한계(공식 정답(C) 기준 하락 포함)는 이 문서가 아니라 [DEC-018](../decisions.md) · [models/registry.md](../../models/registry.md) 에 있다
- 시간은 v2 → 수정 순서로 한 번씩 잰 단일 실행 기술통계다(순서 교차 · 반복 없음). 두 모델의 속도 우열로 읽지 않는다
- 측정 내내 촬영용 터널이 열려 있었다. run.log 의 「127.0.0.1 밖에서 온 요청」은 v2 0 · 수정 0 이고 점검 요청 수도 하네스 것과 같지만, 터널 요청은 프록시를 거쳐 127.0.0.1 로 들어오므로 정밀 판정 폴링(`GET /api/stage2-followup`)까지 하네스 것만이라고 가르지는 못한다. 시간 값에 다른 부하가 섞였을 가능성을 완전히 빼지 못한다
- 조치 위험도 감소율(앱 응답 v2 28.37% · 수정 28.76%)은 1단 스팬 · 위험도 기준선이 모델마다 달라 같은 모집단의 개선량이 아니다. 골드 대조 없이 탐지 개선으로 읽지 않는다
- 측정 장소가 EC2 L4 다. 로컬 PC(RTX 3060) freeze-W12-gguf 의 시간(빠른 결과 약 10초 · 정밀 중앙값 약 27초)과 직접 비교하지 않는다
- `external_llm_used` 는 115계정 기록에 저장하지 않았다. 측정 뒤 메인 계정 1건으로만 확인했다. 외부 연결 감시도 115계정 실행 중이 아니라 측정 뒤 2계정 점검 동안에만 했다

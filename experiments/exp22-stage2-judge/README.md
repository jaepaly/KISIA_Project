# exp22-stage2-judge: 2단 v1 · v2 판정용 평가셋 — **한 번만 채점**

## 1. 왜

2단 v1 은 글 많은 계정에 약하다 — 전체 이력을 넣으면 규칙 판정과 0.653 만 맞는다(exp13). 원인 후보는 길이다: v1 은 길이 1024 로 학습해 긴 예시 68% 를 버렸고, 앱은 실제 계정에 중앙 2,280 토큰을 보낸다 ([exp08 README 「v2 준비」](../exp08-stage2-sft/README.md)). v2 는 실제 크기 계정 · 앱과 같은 입력 · 길이 2048 로 다시 학습한다.

교체를 판정할 셋이 필요하다. **exp09 는 쓸 수 없다** — 1단 test 와 같은 239편이고 불일치 사례를 이미 들여다봤다. 그래서 새 합성 계정으로 만들고, v1 · v2 를 **한 번씩만** 채점한다. exp09 는 v2 가 v1 보다 나빠지지 않았는지 보는 **회귀 확인**으로만 쓴다.

## 2. 규칙 (프로토콜) — 데이터를 만들기 전에 적었다 (2026-10-12)

**무엇을 재나.** 2단 모델은 원문이 아니라 가명화 스팬 목록(유형 · 등급 · 본인 여부 · 글 번호)만 보고, 학습 정답은 규칙(`findings_from_spans`)이다. 그래서 주 지표는 **「앱과 같은 입력을 받았을 때 같은 입력의 규칙 판정과 얼마나 맞나」**다. 입력은 앱 1단(기준선 v2 + 명시 규칙 · 임계값 0.7)이 이 글에서 뽑은 스팬이다 — 두 구성에 같은 1단 출력을 준다.

**두 구성** — 각자의 **전체 구성**으로 돌린다 (모델만 바꾼 비교가 아니다)

| | v1 (지금 앱) | v2 (후보) |
|---|---|---|
| 어댑터 | `exp08 results/adapter` · SHA-256 `1053e7ad…` | `exp08 results/adapter_v2` (학습 뒤 해시를 여기 적는다) |
| system 프롬프트 | `SYSTEM_V1` (infer.py) | `SYSTEM_V2` (make_sft_v2.py — v1 + #296 판정 기준) |
| 입력 고르기 | 상한 24 · 유형당 6 · 스팬 없는 글도 목록에 | 상한 16 · 유형당 4 · 스팬 없는 글 뺌 |
| 출력 예산 · 디코딩 | `output_budget(n)` · greedy — 같다 | 같다 |

**채점하는 출력 두 가지** (Codex 10/12)
- **모델 출력** = 모델이 낸 JSON 을 앱의 `validate_findings` 가 받아 준 결과 — 앱이 실제로 쓰는 모델 판정이다. 파싱 · 검증이 실패하면(앱이 규칙으로 폴백) 그 계정 7칸은 **모델 출력 불일치**로 센다
- **앱 최종** = 앱이 화면에 내는 판정 — 모델 출력이 있으면 그것, 폴백이면 전체 스팬 규칙 판정

**정답 두 가지**
- **같은 입력의 규칙** = 각 구성이 모델에 실제로 보낸 입력(상한 적용 뒤)으로 계산한 규칙 판정 — 「받은 입력에 충실한가」
- **전체 스팬의 규칙** = 1단이 뽑은 본인 스팬 **전부**로 계산한 규칙 판정 (상한 없음 · 두 구성에 같은 정답) — 상한을 줄여 근거를 버리면 여기서 드러난다

**지표** (계정 30 × 7속성 = 210칸)
- **M1 입력 충실도** — 모델 출력 verdict == 같은 입력의 규칙 verdict 인 칸 비율
- **M2 비기권 충실도** — M1 을 같은 입력의 규칙이 abstain 이 아닌 칸만 (분모 0 이면 「해당 없음」)
- **M3 근거 F1** — 모델 출력 evidence(post_id · span_id) vs 같은 입력의 규칙 evidence, 칸 단위 micro. 폴백 계정은 예측 근거 0 으로 센다
- **M4 폴백 수** — 파싱 · 검증 실패로 앱이 규칙으로 떨어진 계정 수
- **M5 앱 최종 일치** — 앱 최종 verdict == 전체 스팬의 규칙 verdict 인 칸 비율 (두 구성에 같은 정답)
- **참고** — 심은 속성 정답(E · E+I → specified · I → narrowed · N → abstain)과의 일치 · 속성별 표 · 추론 시간 · 원시 JSON(검증 전) 기준 M1. 심은 정답은 1단 오류와 표현 등급의 문맥 차이가 섞여 교체 판단에 쓰지 않는다

**교체 기준 — 모두 만족할 때만 v2 로 바꾼다** (DEC-011 「확실히 나을 때만」)
1. M1 이 v1 보다 **0.05 이상** 높고, 계정 단위 paired bootstrap(2,000회 · seed 20261013) 차이의 95% 구간 아래끝이 0 보다 크다
2. M2 가 v1 보다 낮지 않다
3. M3 이 v1 보다 **0.05 넘게** 낮지 않다
4. M4 가 v1 보다 많지 않고 **3계정 이하**
5. **M5 가 v1 보다 0.02 넘게 낮지 않다** — 입력을 줄여 생기는 손실이 앱 최종 판정을 해치지 않는지
6. **exp09 회귀 확인** — 같은 735칸에서 v1(지금 앱 구성)과 v2(v2 구성)를 **같은 채점 경로로 다시** 돌린다(외부 LLM 판정 파일은 9/28 그대로 고정 · 옛 결과 파일은 덮지 않는다). v2 가 v1 보다 전체 일치율에서 **0.03 넘게**, 외부 판정이 abstain 이 아닌 칸에서 **0.03 넘게** 낮지 않다

못 넘으면 v1 을 유지하고 「미채택」으로 기록한다. **10/28(수)까지 판정 · 반영 · 재검증이 끝나지 않아도 v1 유지** (README 「개발 동결」).

**지키는 것**
- 데이터는 생성 → 전수 검토 → 해시로 고정. 그 뒤 바꾸지 않는다. 검토는 1단 · 2단을 돌리지 않고 원문만 본다 — 심은 표현이 의도대로(본인 · 지금 · 남의 정보) 쓰였는지, **심지 않은 개인정보(다른 지명 · 나이 · 직업 · 가족 · 성별 표현)가 끼었는지**(N 칸이 오염되면 그 칸을 참고 지표에서 뺀다), 본문이 잘리지 않았는지
- 1단 예측을 한 번 만들어 고정(해시 · 1단 체크포인트 SHA · 규칙 커밋을 같이 적는다)하고, v1 · v2 를 **같은 날 한 번씩** 돌린다. 결과를 보고 프롬프트 · 상한 · 어댑터를 고치지 않는다 — 고치면 그 뒤 수치는 exp22 로 주장하지 않는다
- v2 의 학습 중 고르기(에폭 등)는 exp08 dev(인물 12명 · 학습에 안 쓴 인물)로만 한다

## 5. 한계

- 사람 글이 아니다(LLM). 독립 단위는 계정 30개다 — 칸 210개를 독립 표본처럼 읽지 않는다(그래서 계정 단위 bootstrap)
- 주 지표는 「규칙대로 판정하나」다 — 2단이 규칙보다 나은 판단을 하는지는 재지 않는다 (학습 정답이 규칙이다)
- v1 과 v2 는 프롬프트 · 입력 상한까지 다르다 — 「어댑터만 바꾼 효과」가 아니라 「구성 전체를 바꾼 효과」다

교체 기준(§2): 1 ✗(M1 +0.057 · bootstrap 95% 구간 −0.076~+0.195) · 2 ✓ · 3 ✓ · **4 ✗(폴백 23)** · 5 ✓ · 6 미실행 → **등록한 기준으로는 v2 미채택**.

**원인 — 앱의 출력 상한(`infer.output_budget`)이 작다.** 폴백 46건 중 45건이 JSON 이 근거 목록 중간에서 잘린 것이다(모델이 형식을 깨뜨린 게 아니다). 상한은 「근거 하나에 약 17토큰」(합성 재현 실측)으로 잡혀 있는데, 이 셋의 스팬 ID(`G22_01_p13_s01`)는 학습 데이터 ID(`B07_b14_s02`)보다 길어 근거 하나에 토큰이 더 든다. 입력 스팬이 15개를 넘는 계정은 v1 · v2 모두 거의 다 잘렸다. 잘리지 않은 계정에서 v2 는 49칸을 모두 규칙대로 판정했다(v1 36칸).

**의미.** 2단 모델의 교체 여부보다 먼저, **지금 앱도 글 많은 계정에서 2단 모델 출력이 잘려 규칙으로 떨어지고 있을 가능성이 크다** — 실제 계정의 ID 형식에서 다시 확인해야 한다. 이 결과는 등록한 대로 기록하고, 출력 상한을 고친 뒤의 수치는 exp22 로 주장하지 않는다 (§2 「결과를 보고 고치지 않는다」). 다시 판정하려면 새 판정셋이 필요하다.

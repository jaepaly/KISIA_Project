# exp28-context-review: 1단 문맥 보정 — 큰 모델이 원문을 읽고 1단을 고치나 · 대신하나 · 모델 크기가 차이를 만드나

**왜** (10/16): 동의받은 실제 블로그 글을 앱으로 점검해 보니(저장소 · 이 실험의 데이터에는 넣지 않는다) 1단(KoELECTRA · 약 1억 파라미터 · 합성 글로만 학습)이 문맥을 못 읽어
- **오탐** — 영상 제목 밈을 장소로, 글쓴이의 아버지를 글쓴이 성별로
- **누락** — 생일 날짜 · 반려동물 이름 같은 강한 단서(지금 단서 유형에 칸이 없다) · 돌려 말한 직업
결론이 「약 6.6만 명 중 한 명 · 추천 없음」으로 나왔다. 규칙 보강(#378)은 본 꼴의 오탐만 줄이고 누락은 그대로다(결론이 오히려 7.9만 명으로).

**2단으로는 못 고친다** — 2단(Qwen3-4B v2)은 원문을 보지 않고 1단이 뽑은 단서의 가명 토큰만 본다(exp22b §2). 1단이 틀리면 그대로 믿고, 놓치면 아예 모른다. 그래서 고칠 곳은 **1단**이다.

**무엇을**: 원문을 읽는 **자체 호스팅 큰 모델(외부 전송 0 — 지금 1단과 같은 서버 안)** 을 1단에 넣는 두 방식을 비교한다.
- **보정(A)** — 1단(KoELECTRA + 규칙) 결과를 받아 ① 문맥상 단서가 아닌 스팬 버리기 · 누구 정보인지(subject) 고치기 ② 놓친 단서 찾기
- **대체(B)** — KoELECTRA 없이 큰 모델이 혼자 단서를 찾는다(명시 규칙만 같이)

모델 크기(4B · 8B · 14B)를 같은 조건으로 비교한다. 흐름: `글 → 1단 [+ 보정 | 대체] → 2단(가명 추론) → k · 추천`

이 문서의 정의 · 기준은 **결과를 보기 전에** 적고 커밋한다(DEC-011 · exp22b · exp27 과 같은 원칙).

## 1. 데이터

## 2. 구성

| 구성 | 1단 | 큰 모델 |
|---|---|---|
| **A0** | v2(`d7dc7b06…`) + 명시 규칙 · 앱 경로(`c1_rules.detect` · `attributes.resolve`) · #378 브랜치(`c8adfe2`) | 없음 — 지금 앱 |
| **A1 · A2 · A3** | A0 | 보정 — Qwen3-4B · 8B · 14B |

- 큰 모델: Qwen3 원본 instruct(어댑터 없음) · 4비트(bitsandbytes nf4) · greedy · thinking 끔 · 출력 JSON. 모두 GPU 서버(L4 24GB)에서 돈다
- 프롬프트 · 출력 형식은 크기끼리 같다(`review.py` 에 고정 · 해시를 결과에 적는다)
- A 입력: 원문 + 1단 스팬 목록(번호 · 문자열 · 유형 · subject). 출력: `drop`(번호) · `subject`(번호 → self/other/unknown) · `add`(글 속 정확한 문자열 · 유형 · subject)
- B 입력: 원문. 출력: `spans`(글 속 정확한 문자열 · 유형 · subject). 명시 규칙 결과와 합친다(앱의 `merge_with_model` 과 같은 방식)
- 유형은 계약 10종 + 측정용 `BIRTHDAY` · `PET_NAME`(계약에 넣지 않는다)
- 프롬프트의 판단 기준에 「단서가 아닌 것: 유행어 · 평가말 / 매체 속 장소 / 성별과 관계없는 호칭」과 「여행으로 잠깐 간 곳은 unknown」을 적는다 — 실제 글에서 본 오탐 **종류**를 일반 지시로 쓴 것이고(#378 규칙과 같은 출발점), 함정 표현 자체는 넣지 않는다. 그래서 T 는 「이 종류를 알려 줬을 때 문맥으로 구분하나」를 잰다
- 모델이 낸 문자열이 글에 그대로 없으면 버린다(지어낸 근거는 세지 않는다 · 2단과 같은 원칙). 여러 번 나오면 모두 스팬으로 둔다

## 4. 판정 기준 (사전 등록)

구성 하나가 아래를 **모두** 만족하면 「채택 후보」다.
1. **T** — A0 대비 **절반 이하**
2. **R** — A0 대비 **−2개 이내**
3. **X** — **12/24 이상** (A0 은 유형이 없어 0 에서 시작)
4. **P** — A0 의 **1.5배 이하**
5. **G** (A 만) — 버린 비율 **3% 이하** · subject 를 틀리게 바꾼 비율 3% 이하
6. **L** — 중앙 **15초 이하** (지금 2단이 점검 한 번에 약 70초 — 글 여러 편을 한 번에 점검하므로 이보다 길면 쓸 수 없다)

- 채택 후보가 여럿이면 **작은 모델 · A 를 먼저** 고른다(지연 · 근거 하이라이트 위치 정확도)
- 「크기가 차이를 만드나」는 A1→A2→A3 · B1→B2→B3 의 T · R · X 를 그대로 적어 답한다
- 채택 후보가 있어도 **10/25 개발 동결 전에 앱에 넣을지는 별도 PM 결정**이다(2단 · 위험도 · 정리서 숫자에 영향). 계약 밖 유형은 k 엔진이 쓰지 못하므로 앱에 넣어도 당장은 「표시만」 된다
- AX · BX 는 판정에 쓰지 않는다

## 5. 한계 (미리 적는다)

- D1 은 합성 글이다 — 블로그 문체를 흉내 낼 뿐 실제 글의 분포가 아니다. 80편 · 묶음당 16~40편이라 경향만 본다

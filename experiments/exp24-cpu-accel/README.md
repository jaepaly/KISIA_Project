# exp24-cpu-accel: 1단 CPU 가속 — 동적 int8 양자화

README W9 D 3번. [필수] 「글 1건 로컬 탐지 지연 < 300ms (CPU)」가 긴 글에서 넘는다 (#301 · v1 · 글별 중앙값의 중앙값 172.92ms · p95 1,006.61ms · 300ms 미만 15/20편). 서버(t3.medium · 2 vCPU)에서는 긴 글 계정 스캔이 40~58초 걸린다 (integration-W08 · 시간의 >95% 가 1단).
**정확도를 바꾸지 않는 가속만** 본다. 이 문서의 기준은 **정확도를 보기 전에** 적고 커밋한다 (DEC-011 과 같은 원칙 — 결과를 보고 기준을 바꾸지 않는다).

## 1. 사전 탐색 (2026-10-13 · 속도만 · 정확도는 보지 않았다)

test 가 아닌 글 20편(길이순 등간격 — `measure_cpu_latency.select_length_spaced` · 147~2,595자) · v2 체크포인트(`model.safetensors` SHA-256 `d7dc7b06…`) · 모델 단독 `SpanDetector.detect()` · 글마다 워밍업 2 · 측정 5 · Ryzen 5 5600X.

- 시간의 **99% 가 모델 계산(forward)** 이다. 토큰화 · 후처리 · 계약 검사는 1% 미만 — 줄일 곳은 모델 계산뿐이다
- 긴 글의 창(256토큰 · stride 64)은 **이미 배치로 한 번에** 돈다(`batch_size=16`). README 의 「창 배치」 후보는 이미 들어 있어 뺀다

| 구성 | 스레드 | 중앙값 | p95 | 최대 |
|---|---:|---:|---:|---:|
| fp32 (지금) | 4 | 172.6ms | 748.7ms | 1,230.3ms |
| int8 동적 양자화 | 4 | 95.6ms | 375.3ms | 643.3ms |
| fp32 | 2 | 207.1ms | 953.4ms | 1,584.7ms |

## 2. 후보 (PM 결정 10/13 — (가))

**PyTorch 동적 int8 양자화** — `torch.quantization.quantize_dynamic(model, {torch.nn.Linear}, dtype=torch.qint8)`. 가중치를 불러온 뒤 메모리에서 바꾼다 — 체크포인트 파일은 그대로다. 새 의존성 없음.
ONNX Runtime 은 보지 않는다 — 변환 단계와 서버 · 시연 PC 설치가 늘어 10/22 안에 판정 · 반영을 끝내기 어렵다.

## 3. 데이터 — test · exp17b · exp17c 는 보지 않는다

| 셋 | 무엇 | 쓰는 곳 |
|---|---|---|
| **dev 골드** | 코퍼스 v0 골드 중 test(`splits/test_post_ids.json` 255편)가 아닌 글 **2,512편** · 정답 스팬 2,622개 | 스팬 일치 · partial F1 |
| **exp17** | 개발용 심은 단서 80편 | 스팬 일치 · 본인 재현율 |
| **지연 20편** | dev 골드에서 길이순 등간격 20편 (§1 과 같은 함수 · 같은 글) | 지연 |

⚠️ dev 골드는 1단 학습에 쓴 글이라 F1 절댓값은 부풀려져 있다. 여기서는 **기준선과 후보의 차이만** 본다.

## 4. 재는 경로 — 앱 탐지 경로 전체

앱이 실제로 부르는 길 그대로 — `apps/analyzer/engines/c1_rules.detect` (모델 `predict_raw` → 명시 규칙 병합 `rules.merge_with_model` → `format_contract` · level · subject 판정). 체크포인트 v2 · 임계값 0.7 · 규칙 켬 (`C1_RULES` 기본). 입력 채널은 글의 `title` · `body` · `photo_caption:N` 그대로.
기준선과 후보는 **같은 PC · 같은 스레드 수**로 잰다. 지연은 **모델 단독**(`SpanDetector.detect`)도 따로 적는다 (#301 과 비교용).

## 5. 채택 기준 — 셋 다 만족해야 채택

1. **스팬 일치** — dev 골드 2,512편 + exp17 80편에서 앱 경로 출력 스팬 `(post_id, text_id, start, end, type)` 의 집합 일치율 |기준선 ∩ 후보| / |기준선 ∪ 후보| **≥ 0.98**
2. **정확도**
   - dev 골드 partial F1 (type 일치 + IoU ≥ 0.5 · `train.score_span_sets` · 전체) 하락 **≤ 0.005**
   - exp17 본인 재현율 (`exp17-planted-eval/score.py`) 하락 **≤ 1건**
3. **속도** — 지연 20편 · 앱 경로 · 글별 중앙값(워밍업 3 · 측정 10)의 **p95(nearest-rank)가 30% 이상 감소** — 4스레드 · 2스레드(서버와 같은 vCPU 수) **각각**

하나라도 못 미치면 채택하지 않고 「긴 글은 300ms 를 넘는다」를 한계로 적는다 (README 성공 기준 표에 이미 그렇게 쓰고 있다). 기준선에 못 미친 이유는 적되 **기준을 고쳐 다시 재지 않는다.**

## 6. 채택하면

- `SpanDetector(quantize="int8")` 옵션 · 앱 기본 켬 · `C1_QUANT=0` 이면 끔 (`C1_RULES` 와 같은 방식) · `/api/engine-mode` 에 표시
- registry 1단 v2 행에 「CPU 추론 int8 동적 양자화(로드 시 변환 · 파일 동일)」 한 줄
- 서버(veilo.site)에서 같은 20편을 다시 재서 적는다 (기기 차이 확인용 · 판정에는 안 쓴다)
- 최종 숫자는 10/29 러너가 #301 과 같은 test 20편으로 잰다 (지연만 · 정답은 안 연다)

## 7. 결과 (2026-10-13 · 이 PC Ryzen 5 5600X · torch 2.12.1 · `bash pipeline.sh <v2 폴더>` → `python score.py`) — **미채택**

§5 기준 넷 중 셋 미달. **속도는 줄지만 모델 출력이 무너진다.**

| 기준 | fp32 (지금) | int8 | 판정 |
|---|---:|---:|---|
| 1 스팬 일치 (dev 2,512 + exp17 80) | 스팬 3,818 | 스팬 514 · 일치율 **0.066** | 미달 (≥ 0.98) |
| 2a dev 골드 partial F1 | 0.690 (P 0.596 · R 0.818) | 0.205 (P 0.762 · R 0.118) | 미달 (하락 0.485 · 허용 0.005) |
| 2b exp17 본인 재현율 | 102/119 | 58/119 | 미달 (하락 44건 · 허용 1) |
| 3 앱 경로 p95 — 4스레드 | 701.0ms | 345.7ms (−50.7%) | 통과 |
| 3 앱 경로 p95 — 2스레드 | 907.9ms | 592.6ms (−34.7%) | 통과 |

- 지연 20편 · 앱 경로 글별 중앙값의 중앙값: 4스레드 153.8 → 106.6ms · 2스레드 227.5 → 123.1ms · 300ms 미만 14 → 18편(4스레드). 모델 단독도 같은 크기 (`results/latency_*.json`)
- **왜 무너지나 (결과 뒤 진단 · exp17 20편)**: 임계값 0 으로 후보를 다 뽑아도 fp32 · int8 스팬이 하나도 같지 않다(일치율 0.0). 스팬 점수 중앙값 0.904 → 0.239, 토큰 태그(argmax) 일치 0.84, 로짓 차이 최대 7.1. Linear 층 int8 동적 양자화가 이 KoELECTRA 미세조정 모델의 출력을 크게 흔든다 — 임계값 문제가 아니다
- 판정 뒤 다른 양자화 변형(분류 층 제외 등)을 같은 dev 로 다시 고르지 않았다 — 고른다면 새 후보로 명세부터 다시 쓴다

**결론** — 1단 CPU 가속은 채택하지 않는다. README 성공 기준 「글 1건 < 300ms」는 지금처럼 「중앙값은 미만 · 긴 글은 넘는다」로 적는다. 앱 · registry 는 바꾸지 않는다.
